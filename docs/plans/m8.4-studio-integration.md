- [Playground package](https://github.com/mastra-ai/mastra/blob/mastra%401.25.0/packages/playground/package.json): private package with workspace dependencies on Core, client-js, playground-ui, react, ai-sdk and schema-compat. A fork therefore needs the pinned upstream workspace build toolchain, not just copying one component.
- [Vite build](https://github.com/mastra-ai/mastra/blob/mastra%401.25.0/packages/playground/vite.config.ts): generates the Studio route manifest from source. Do not edit the compiled manifest to pretend a React route exists.

A read-only GET of existing `http://localhost:4111` returned 200, title `Mastra Studio`, with entry asset `index-CQRwqJjx.js`, matching the installed Studio HTML. That installed entry imports `main-KfoT5ar4.js`. This verifies that Studio is reachable; it does **not** verify an Organization page. No existing Mastra process was changed.

**Conclusion:** No officially supported native sidebar/page registration API was found in this installed release. `registerApiRoute()` creates server routes; it does not create Studio navigation items or React routes. The public [custom API route documentation](https://mastra.ai/docs/server/custom-api-routes) and [Studio hosting documentation](https://mastra.ai/docs/studio/deployment) describe these distinct facilities.

## Same-origin options investigated

| Option | Meets the requested existing-sidebar experience? | Decision |
| --- | --- | --- |
| Serve Control Center at `/organization` using custom HTTP handlers | No: direct URL works, but the unmodified Studio sidebar/router does not contain the entry | Insufficient on its own |
| Reverse-proxy Studio and Control Center under localhost:4111 | Same-origin hosting is possible, but it still cannot add an existing-sidebar entry; also requires moving the already-running service to another port | Not the minimal solution |
| HTML/JavaScript injection, DOM mutation, compiled bundle patch | Could force a link but relies on undocumented DOM/runtime internals; not a supported extension | Reject; no injection or artifact patching |
| Pinned Studio source build with an Organization route and sidebar item; same-origin embedded Control Center | Yes, subject to implementation and browser verification | Recommended, **requires approval for a maintained source fork** |

`MASTRA_STUDIO_PATH` is a documented way to serve a separately built SPA alongside Mastra. It is a supported **hosting mechanism**, not official support for the custom frontend changes. The fork output can live in a project-owned build directory; no need to patch node_modules or `.mastra/output`.

## Minimal proposal to approve

1. Pin the upstream Studio source to `mastra@1.25.0` and record its resolved commit/checksum. Build in a separate source checkout with its own lockfile/toolchain. Preserve the upstream license and keep a small reviewable patch series. Do not install the whole Studio workspace into the runtime's root dependency tree.
2. Add `Organization` to `src/lib/nav/nav-items.tsx`, add `/organization/*` beneath the existing Studio root layout in `src/App.tsx`, and add one Organization page. Check the existing route-permission map; explicitly gate the page consistently if auth is enabled rather than bypassing the guard. Keep Agents, Workflows, Observability/Traces and all existing navigation unchanged.
3. The new page hosts a **same-origin iframe** with a meaningful accessible title, loading/error fallback, and the existing Control Center content. Use a small embed mode to remove only the duplicate outer Control Center sidebar/header; keep hierarchy, inspector, neutral tokens and compact view navigation. Objectives, Runs, Reviews and Overview remain available inside that content. The iframe isolates CSS/React dependencies and avoids copying Studio providers into our UI. No separate browser tab or 4310 connection is needed.
4. Serve Control Center static assets at a namespaced path such as `/organization-app/` and its read-only API/SSE at `/api/control-center/v1/*` through supported Mastra custom HTTP routes. Reuse the Gateway reader and wire schemas. Refactor transport framing into a shared helper if necessary; no second scheduler/database, no provider probes, no execution methods. Use explicit allowlisted static paths and same-origin/auth checks. Do not forward arbitrary routes or relax the existing read-only boundary.
5. Only the embedded asset response may use `frame-ancestors 'self'` (the existing standalone response forbids framing). Make asset/API bases configurable, because the current UI assumes root `/app.js`, `/app.css`, `/api/v1/*`. Streaming must stay unbuffered and resume with the same durable cursor; token snapshots remain replacements.
6. Serve the **built fork** using `MASTRA_STUDIO_PATH` through the supported hosting path. Retain the normal Mastra build pipeline; do not edit generated output. Coordinate the switch/restart of the current localhost:4111 process after approval, without interrupting active execution. No service changes were made as part of this proposal.
7. Keep links into existing Mastra run/Observability pages on the same origin and navigate the parent Studio tab when appropriate. The current schema exposes run links but no authoritative trace IDs: missing trace mappings stay UNKNOWN. Do not invent trace IDs or rebuild the trace viewer.

The Gateway remains read-only. Existing Studio features retain their existing capabilities; the new Organization page introduces no Submit/Approve/Cancel/model-execution controls.
