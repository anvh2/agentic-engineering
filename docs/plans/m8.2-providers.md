## Phase 0: what was wrong and what changed

M8.1 finding: scheduler stop and `lead cancel` left the Mastra run, its inference and its model permit alive. Traced chain: CLI -> scheduler -> executor -> Mastra HTTP -> workflow step -> runner -> provider call -> permit.

| Gap | Fix |
| --- | --- |
| `Scheduler.stop()` failed the task but never cancelled the run | stop cancels each in-flight run and **confirms** it (run terminal AND no permit held/queued for the task); `run()` returns only afterwards; unconfirmed runs are in `RunSummary.stillActive` |
| `lead cancel` only wrote `CANCELLED` | writes the fence first, then cancels and confirms the run; idempotent retry; exit code 1 unless confirmed |
| A lease lost to an operator cancel only logged | cancels the run (an *expired* lease deliberately does not: the next claim adopts it) |
| A run started after the task lost its fence was never recorded, so nothing could stop it | cancelled by id |
| New work could be claimed during shutdown | gate re-checked per claim; a stopping scheduler claims nothing |
| A result arriving in the same tick as a timeout could still be recorded | discarded (fencing preserved) |
| Verification subprocesses ignored cancellation; the retry delay was not abortable | process group killed on abort; a cancel landing as the model returns skips verification and cannot yield PASS |
| A provider ignoring its abort left no trace and released the permit | reported (`provider_unresponsive`); permit stays held until it really settles |
| A second Ctrl-C did nothing | second signal exits at once and prints the runs that may still be running |

Every cancellation writes an audit event (`run cancellation (<reason>): <outcome>`). Crash, lost-lease, timeout and concurrent-shutdown cases are covered in `cancellation.test.ts`; the Mastra HTTP semantics in `client-cancel.test.ts` (in-process fake).

Known limit: a Mastra step between tool calls only observes the abort at its next await.

## Phase 1: contract

See `docs/architecture/runtime.md#worker-providers`. A provider is a `WorkerLike` plus a `ProviderDescriptor`; the runner remains the only execution path and the only source of PASS. Unreported measurements are the literal `UNKNOWN`. Each provider queues on its own machine-wide capacity resource.

## Phase 2: Codex adapter: risks to confirm in the real smoke test

All unverified because there is no real CLI to observe:

1. The installed `codex exec --help` actually lists `--sandbox` and `--cd` (the adapter refuses to run otherwise).
2. `codex exec` in `workspace-write` does not wait on an approval prompt (a hang would be bounded by the deadline and killed).
3. Whether `workspace-write` blocks writes to the worktree's `.git`. The adapter rejects a moved `HEAD`, but a CLI that rewrote refs or the index without moving `HEAD` is not detected beyond the runner's file comparison.
4. The `--json` event shape (usage / tool evidence). Parsing is tolerant; if the shape differs, usage is `UNKNOWN`, which is safe but unhelpful.
5. How the CLI authenticates under the allowlisted environment (`HOME` is forwarded; `CODEX_HOME` and API keys only if named in `passEnv`).
6. Whether usage is metered (API key) or subscription quota: billing is declared `unknown` and cost/quota are `UNKNOWN`.
