## Phase 0: what was wrong and what changed

M8.1 finding: scheduler stop and `lead cancel` left the Mastra run, its inference and its model permit alive. Traced chain: CLI -> scheduler -> executor -> Mastra HTTP -> workflow step -> runner -> provider call -> permit.

| Gap | Fix |
| --- | --- |
| `Scheduler.stop()` failed the task but never cancelled the run | stop cancels each in-flight run and **confirms** it (run terminal AND no permit held/queued for the task); `run()` returns only afterwards; unconfirmed runs are in `RunSummary.stillActive` |
| `lead cancel` only wrote `CANCELLED` | writes the fence first, then cancels and confirms the run; idempotent retry; exit code 1 unless confirmed |
| A lease lost to an operator cancel only logged | cancels the run (an *expired* lease deliberately does not: the next claim adopts it) |
| A run started after the task lost its fence was never recorded, so nothing could stop it | cancelled by id |
| New work could be claimed during shutdown | gate re-checked per claim; a stopping scheduler claims nothing |
| A result arriving in the same tick as a timeout could still be recorded | discarded (fencing preserved) |
| Verification subprocesses ignored cancellation; the retry delay was not abortable | process group killed on abort; a cancel landing as the model returns skips verification and cannot yield PASS |
| A provider ignoring its abort left no trace and released the permit | reported (`provider_unresponsive`); permit stays held until it really settles |
| A second Ctrl-C did nothing | second signal exits at once and prints the runs that may still be running |

Every cancellation writes an audit event (`run cancellation (<reason>): <outcome>`). Crash, lost-lease, timeout and concurrent-shutdown cases are covered in `cancellation.test.ts`; the Mastra HTTP semantics in `client-cancel.test.ts` (in-process fake).

Known limit: a Mastra step between tool calls only observes the abort at its next await.

## Phase 1: contract

See `docs/architecture/runtime.md#worker-providers`. A provider is a `WorkerLike` plus a `ProviderDescriptor`; the runner remains the only execution path and the only source of PASS. Unreported measurements are the literal `UNKNOWN`. Each provider queues on its own machine-wide capacity resource.

## Provider selection (manual, one task at a time)

- **Existing mechanisms checked first.** Nothing selected a worker per task (`executor: worker|claude` is a different axis; the Lead's objective plans emit only `{contract, assessment}` and cannot carry a provider). The delegation `request` already travels unchanged from the task spec through the scheduler and executor into the workflow, so one optional field is the whole channel: `request.provider` (default `ollama`).
- **Operator-controlled authorization.** A task can only *request* a provider. A non-default provider runs only if the operator allows it with `AGENTIC_ALLOW_PROVIDERS` and/or `lead run --allow-provider`, entries `codex` (any task) or `codex:<taskId>` (that one task). It is enforced twice, independently: by the scheduler before a worktree is prepared or an executor is called (`provider_not_authorized`), and by the workflow in the process that would spawn the CLI (the Mastra server's own environment). Neither a plan nor a Lead can authorize it.
- **No fallback, no cloud retry.** Unknown/unavailable provider -> the task fails (`provider_unavailable`); nothing else is tried. Cloud tasks get at most 2 coding attempts and 0 automatic runtime retries (`ProviderDescriptor.limits`); a lease that expires on a non-default-provider task (or `lead resume --steal`) goes to `RUNTIME_FAILURE` instead of being requeued, so a lost lease can never start a second automatic paid call. `lead retry` remains the explicit human decision. `lead tasks` shows `provider=codex` on such tasks.
- Preserved unchanged: SQLite fencing, worktree isolation, runtime-only PASS, cancellation propagation.

## Sandbox preflight (`codex sandbox`, local, no model, disposable fixture)

Fixture mirrored the smoke layout (repo + `git worktree` + sibling dirs) under gitignored `.workdir/` (a first run under `/tmp` was discarded because `/tmp` is itself writable and confounded the result). `codex sandbox` has no `--sandbox` flag; it was run with the built-in profiles `-P :workspace` and `-P :read-only` (control). Equivalence of `:workspace` to `exec --sandbox workspace-write --ignore-user-config` is **assumed, not proven**.

| Probe (commands run inside the sandbox, cwd = the task worktree) | `:workspace` |
| --- | --- |
| write inside the worktree | allowed |
| write to a sibling dir, the worktree's parent, the source repo's working tree | **denied** |
| write to the source repo's `.git` (file and `objects/`) | **denied** |
| write to the worktree's gitdir (`repo/.git/worktrees/<name>`), append to the worktree `.git` file | **denied** |
| `git add` / `git commit` in the worktree | **fails** (cannot create `index.lock`); `git status` works |
| create `.codex/` or `.agents/` in the worktree | **denied** |
| write through a symlink pointing outside / into `repo/.git` | **denied** |
| write to `$HOME` | **denied** |
| write to `$TMPDIR` and `/tmp` | allowed (`/var/tmp` was denied in the first, `/tmp`-hosted run) |
| outbound network (DNS/HTTPS) | blocked (host not resolved) |
| read a file outside the writable root (a sentinel; the enclosing project's `AGENTS.md`) | **allowed** |
| control: `:read-only`, write inside the worktree | denied (so the profile selection is honoured) |

Conclusion: the minimum isolation (writes confined to the worktree plus temp dirs, git metadata protected, no commit possible, no network) is enforced by the installed CLI for commands the model runs. Not claimed: complete filesystem isolation.

## Sandbox limitations and outstanding security risks

Status after the preflight and the smoke (items marked **observed** were checked; the rest remain unverified):

1. **Writable scope is the whole worktree, not the allowed file.** `workspace-write` cannot express "only this file". Bounded by the runner's filesystem comparison (forbidden change -> reverted, task fails) and by the review gate.
2. **`.git` access: observed protected** (see the preflight; commit/stage fails, gitdir and `.git` file are not writable). Original concern: A task worktree's `.git` is a *file* pointing into the source repo's `.git/worktrees/<name>`, which is outside the worktree directory and so should not be a writable root; Codex also protects `.git` paths inside writable roots (to be confirmed). Bounded by: HEAD movement is rejected, and the smoke report records whether any pre-existing ref changed. A change that rewrote the index or loose objects without moving HEAD is not specifically detected beyond the file comparison and `git fsck`.
3. **Other writable directories: observed** `$TMPDIR` and `/tmp` writable, `$HOME` and `/var/tmp` not, network blocked. Original text: `workspace-write` normally also allows the temp directories (`$TMPDIR`, `/tmp`) and `CODEX_HOME` state (sessions, unless `--ephemeral`, which is used when advertised). Network is expected off by default inside the sandbox. Not observed.
4. **Approvals: no hang observed** in the one real run. Original text: `exec` has no approval flag; with `--ignore-user-config` the CLI's non-interactive default applies. A hang waiting for approval would be killed by the deadline. Unverified.
5. **Credentials.** The CLI authenticates from `CODEX_HOME`/`HOME`; both reach the child. The model-generated commands run inside the CLI's sandbox, but the CLI process itself holds the credentials and talks to the network. No API key is forwarded unless named in `AGENTIC_CODEX_PASS_ENV`.
6. **Billing is unknown** (`billing: unknown`): subscription quota vs API metering depends on how Codex is signed in. Cost and quota are recorded as `UNKNOWN`, never 0.
7. **`--json` event shape: usage parsed in the real run**; parsing is still tolerant; if it differs, usage and tool evidence are `UNKNOWN` (safe, less informative).
8. **(Resolved for one run by the HTTP smoke below.) The in-process smoke executor skips the HTTP hop** to a Mastra server. Authorization is enforced in the workflow's own process; when running through `npm run dev` the operator must set `AGENTIC_ALLOW_PROVIDERS` in the server's environment too, or the task is refused (fail closed).
10. **Read access is broad (observed).** Commands run by the model can read files outside the worktree (a sentinel and the project's `AGENTS.md` were readable); whether private paths such as `~/.ssh` or `~/.codex` are readable was deliberately NOT probed. Anything the model reads is sent to OpenAI. Do not run the smoke or real tasks on a machine/account where that matters without a profile that restricts reads.
11. **The Codex CLI process itself is not sandboxed** and keeps writing its own state (e.g. under `~/.codex`) and refreshing credentials; this was not inspected and is outside the disposable fixture.
12. **Cancellation was not exercised against real Codex, in either smoke** (mock only; the HTTP cancellation tests use a fake CLI), and a hard `kill -9` of node cannot be handled.
9. **Codex output quality**: comment deletion and unintended edits are measured by the report (`commentsKept`, `forbiddenFiles`), not prevented.
