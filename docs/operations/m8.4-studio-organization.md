# Pinned Organization integration

This is an explicitly maintained Studio source fork, not an official frontend plugin. The installed Studio release has no supported sidebar extension registry. The supported `MASTRA_STUDIO_PATH` hosting mechanism serves our separately built SPA; supported custom HTTP routes serve the existing read-only Gateway on the same Mastra origin.

Upstream: `mastra@1.25.0`, commit `c5702d34a575742e7b7e922d370a67b39e418d4f`. Archive checksum and pnpm pin: `upstream.json`. Runtime compatibility: `mastra@1.25.0`, `@mastra/core@1.59.0`, `@mastra/deployer@1.59.0`.

Only four upstream source paths change in `organization.patch`:

- `packages/playground/src/lib/nav/nav-items.tsx`: Organization sidebar entry.
- `packages/playground/src/App.tsx`: `/organization/*` inside Studio's existing layout and permission guard.
- `packages/playground/src/domains/auth/route-permissions.ts`: `observability:read` mapping.
- `packages/playground/src/pages/organization.tsx`: same-origin iframe with loading/unavailable state and origin-checked ready acknowledgement.

One further upstream path changes in the separate `upstream-build-fix.patch`, which is a build fix and not a feature: `packages/playground-ui/src/domains/memory/components/flame-graph.tsx:271` annotates a Scatter `shape` callback as `{ cx?: unknown }` instead of `Record<string, unknown>`. At the pinned commit, the lockfile's `recharts@3.8.1` `ScatterShapeProps` has no string index signature, so upstream's own `vite-plugin-dts` gate fails `@mastra/playground-ui`. The emitted JS is unchanged. Drop this patch when an upgrade's pin builds without it.

Full upstream source stays ignored in `.workdir/studio-source`; no upstream source tree is committed. No `node_modules` or generated `.mastra/output` files are patched. Upstream includes Apache-2.0, enterprise-directory and third-party licensing: retain `LICENSE.md`, `ee/LICENSE` and original dependency notices when distributing. The build copies upstream notices alongside the SPA.

## Build and launch

Use Node 22.23.2 or a compatible Node 22 release; upstream pnpm 11 is installed in an isolated npm cache by the build script. Root runtime and UI dependencies must already be installed (`npm ci`, `npm ci --prefix apps/control-center` in a fresh checkout).

```sh
npm run build --prefix apps/control-center
node studio-fork/build.mjs
MASTRA_TELEMETRY_DISABLED=1 npm run build -- --studio
AGENTIC_SCHED_DB=/absolute/path/to/existing/.workdir/scheduler/scheduler.db node studio-fork/start.mjs
```

Open `http://127.0.0.1:4111`, then **Organization**. `http://localhost:4111` uses the same loopback listener. No 4310 server is needed. `PORT=4411` can be used for isolated verification if 4111 is occupied; this does not satisfy final 4111 acceptance.

`start.mjs` refuses occupied ports, binds 127.0.0.1, does not load `.env` or inherit provider credentials, and does not start a scheduler or workflow. It runs the real built Mastra configuration with isolated preview Mastra storage under `.workdir/control-center-runtime`. Point `AGENTIC_SCHED_DB` at the existing task database: the Gateway opens it read-only and never copies it. Missing DBs yield disconnected/UNKNOWN. Historical workflow links may not resolve in the isolated preview's empty Mastra storage; this is not evidence that the original run is absent.

`--studio` is required: without it `mastra build` emits `createNodeServer(..., { studio: false })`, `MASTRA_STUDIO_PATH` is ignored and `/` serves Mastra's welcome page. `start.mjs` refuses such a runtime.

For an owner-approved launch of the existing runtime with its original Mastra storage, build it with `--studio`, preserve its normal working directory and storage configuration and add:

```sh
CONTROL_CENTER_ENABLED=1 \
CONTROL_CENTER_ASSETS_DIR=/absolute/path/to/apps/control-center/dist \
CONTROL_CENTER_STUDIO_ORIGIN=http://localhost:4111 \
MASTRA_STUDIO_PATH=/absolute/path/to/.workdir/studio-dist \
MASTRA_HOST=127.0.0.1 \
node .mastra/output/index.mjs
```

The owning session must perform that switch when safe. This work never stops or restarts an unrelated server. Existing Studio execution controls retain their upstream behavior; Organization itself has no write controls. Do not click execution controls during read-only verification.

## Routes and trust boundary

- `/organization/*`: native Studio frontend route, not a custom HTTP endpoint.
- `/organization-app/`, `app.js`, `app.css`: allowlisted Gateway assets.
- `/control-center/v1/snapshot`, `/events`, `/collaboration`, `/collaboration/{threads,sessions}/:id`, `/collaboration/events`: read-only same-origin Gateway. It is not under `/api`, because `@mastra/core` 1.59 reserves the `apiPrefix` for built-in routes and refuses to start when a custom route uses it.
- All other paths in those namespaces return 404; non-GET methods return 405.

Gateway routes preserve Mastra auth and require `observability:read` when RBAC is enabled. They additionally require a loopback host and same-origin requests. Embedded assets permit only same-origin framing; standalone assets prohibit framing. The preview is a local trusted-user tool; it is not a public multi-tenant deployment. Header-only Studio auth is not forwarded into the iframe: unsupported auth modes fail closed, and cookie-based authenticated embedding must be separately verified before deployment.

The existing scheduler adapter remains the source of task/activity truth; no scheduling, permits, schemas, provider adapters, verifier logic or Core instrumentation changes. Verifier is shown as an architectural role with UNKNOWN identity/activity; no invented agent process. The objective DAG is an accessible dependency-edge table. Raw review payloads are not exposed; review IDs, task state and chronology remain visible. Trace IDs, pricing, invocation usage and missing heartbeats remain UNKNOWN rather than guessed.

Discussions and Meetings read Core B's persisted `collab_events` from the same scheduler database (`AGENTIC_SCHED_DB`). The connection is read-only, and a broken hash chain or a missing append-only guard is shown as an integrity failure, not as empty data. See `docs/architecture/m8.4-collaboration-ui-contract.md`.

To see a meeting without a model, seed Core B's deterministic fake-agent reference meeting into a NEW database. The seed script refuses an existing file. `--from` copies an existing scheduler database through a read-only connection, so the Organization views keep its real data:

```sh
node src/integrations/control-center/__testing__/seed-collaboration-demo.ts .workdir/m9-collab-demo/scheduler.db \
  --from /absolute/path/to/existing/.workdir/scheduler/scheduler.db
PORT=4411 AGENTIC_SCHED_DB=$PWD/.workdir/m9-collab-demo/scheduler.db node studio-fork/start.mjs
```

Its participants are Core B's scripted test identities (`provider: fake`), and the UI labels the transcript "DETERMINISTIC FAKE PARTICIPANTS ... Not live model output". Never point the seed script at a live scheduler database.

## Agents and Council (read-only aggregation)

Two more Organization tabs read sources that already exist. Neither adds a store, a meeting engine or a write path.

- **Agents** (`/control-center/v1/agents`) lists what this Mastra process registered, read from the registration objects that `new Mastra({ agents })` holds:
  - coding workers;
  - read-only specialists;
  - the council's SCRIPTED stand-ins.

  For each agent it shows the resolver's model binding (`provider/model`) and a status. A specialist the model registry refused is `unavailable` when its provider or model is unavailable, and `refused` otherwise (unauthorized, unknown, incapable, missing credential); the resolver's code is the reason. A specialist repointed after binding (Studio's model picker) is flagged `REPOINTED`. Model availability is not probed.
- **Council** (`/control-center/v1/council`, `/council/events`) shows engineering council meetings.
  - The meetings are Core B meetings in the council's own database, `<workdir>/council/council.db`. They are read with the **same** read-only, hash-chain-verified collaboration reader as the scheduler's meetings: proposals, objections, decisions, timestamps and participants come from the verified events.
  - The council's own files add the mode (LIVE or SCRIPTED), the recorded model, model and tool call counts, the record path, the Mastra workflow run link and the trace ids. They are shown only when the council record's meeting-record hash, chain hash and event coverage equal what Core B verified, and when the participants' identities match the claimed model. Otherwise the meeting is shown from Core B alone, with a "COUNCIL RECORD NOT VERIFIED" notice.
  - A store without its append-only guards is `CORRUPT`, never an empty list.

The council records are read from `<project root>/.workdir` (where `npm run council` writes). `CONTROL_CENTER_COUNCIL_WORKDIR=/abs/path/.workdir` points at another checkout's records instead; it is read-only. `studio-fork/start.mjs` forwards it.

Workflow-run links point at `CONTROL_CENTER_STUDIO_ORIGIN`. Traces live in the Mastra storage of the server that ran the council. The isolated `start.mjs` preview has empty storage, so open the run on the server that executed it (e.g. the dev server on 4211) when the preview cannot resolve it.

### Putting it on 4111 without touching another session's process

`start.mjs` refuses an occupied port and never stops or replaces a server. If 4111 is held, find out who owns it, read-only:

```sh
lsof -nP -iTCP:4111 -sTCP:LISTEN    # the PID
ps -o pid,etime,command -p <PID>     # what it is and how long it has run
lsof -a -p <PID> -d cwd              # which checkout it runs from
```

Only the owning session, or the human, stops that process: Ctrl-C in its terminal, or `kill <PID>` by the person who started it. Then, from the checkout that has this change:

```sh
npm ci && npm ci --prefix apps/control-center        # fresh checkout only
npm run build --prefix apps/control-center
node studio-fork/build.mjs                           # or reuse an identical .workdir/studio-dist (same studio-fork/* pins)
MASTRA_TELEMETRY_DISABLED=1 npm run build -- --studio
PORT=4111 \
  AGENTIC_SCHED_DB=/abs/path/to/.workdir/scheduler/scheduler.db \
  CONTROL_CENTER_COUNCIL_WORKDIR=/abs/path/to/checkout-that-ran-councils/.workdir \
  node studio-fork/start.mjs
```

Open `http://127.0.0.1:4111/organization`. This launch does not load `.env`: no provider keys and no Mastra platform token reach the process.

## Upgrade and rollback

Each upgrade must pin a new upstream commit/archive checksum and compatible runtime packages, reapply the four-file source patch, inspect route/auth/theme changes, rebuild and repeat browser/navigation/SSE tests. Estimate 2–4 hours for a straightforward rebase; one day or more for router/auth/workspace changes. Build tooling and the large upstream workspace are version-coupled, although our Control Center React dependencies remain isolated.

Rollback: the owning session removes `CONTROL_CENTER_ENABLED` and `MASTRA_STUDIO_PATH` from its launch configuration and restarts when safe. Mastra then serves its original installed Studio; Gateway routes are not registered. No scheduler/database rollback is necessary. Keep existing artifacts until the owning session confirms they are unused; never reset another worktree or patch generated assets.
