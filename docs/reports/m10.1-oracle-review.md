## 3. Findings

### BLOCKERS

**B1 (cheat f) run-id overlap is never exercised.** Fix: add a case with two live runs of one task and ids that overlap on purpose, then assert each cancel sees only its own permit, in both directions:
- `run-1` vs `run-10`;
- a delimiter-bearing pair, `r` vs `r:1` (Mastra lets the client choose the runId, so `:` is legal);
- a run id equal to another part of the holder: label `fake:model`, task `T`, pid. For example a run named `fake` or `model` or `T` must stay `stopped` while `run-9` holds a permit.
A `holder.includes(runId)` matcher fails these.

**B2 (cheat j) foreign queue entry is never shown to be harmless.** In case 3, `rb` tests B's cancel (A's lease ignored) but A's cancel is only asked (l.242) after B has left the queue (l.238-240). An engagedBy that scopes leases by run but still matches waiters by `w.tag === tag` (the baseline line, model-capacity.ts:185) passes every case. Fix: while B is still queued, assert (i) `cancelRun(run-A)` is `still_active` with `engaged.length === 1` and `kind === 'lease'`, (ii) `cancelRun(run-C)` (holds nothing) is `stopped` with both A's lease and B's waiter present. F2-b explicitly says "permit or queue entry".

**B3 Cases 9a/9b over-pin the implementation (would reject a correct fix).** They copy `live.holders()[0].holder` and replay it with `crashed.tryAcquire(holder)` (l.356, 360, 377-378). `tryAcquire(holder)` has no tag or option parameter. A correct implementation that carries ownership in a separate column or in `AcquireOptions.runId` (the cleaner design) loses the run id on replay, so the lease is "unknown ownership", fails closed, and 9b's `run-2 -> stopped` (l.379) fails. The operator already warned against depending on the holder string format. Fix: simulate the crash agnostically: while the real run is live, `SELECT * FROM leases` through `node:sqlite` on `db`; after `finish(run)` re-insert that row (new `id`, `expires_at = clock.t + leaseMs`). Every column the implementation added is copied. Alternatively pin the API in the header (e.g. `tryAcquire(holder, {runId})`).

**B4 Harness converts failures into hangs; no verdict.** `await a.entered` (l.184, 215, 255, ...) and `await x.done` have no timeout. `runCodingTask` returns before the model call when `sandboxStatus()` is unavailable (runner l.351-374; sandbox.ts:166-172 supports macOS only), when an implementation throws on a new `runId` validation, or when it routes acquisition around `capacity.acquire`. `entered` then never resolves and node:test has no default timeout, so the oracle hangs instead of failing. The 8b Proxy (l.109-120) only intercepts `acquire`; an implementation that acquires through another method never triggers `onPermit`, `abort` is never called, and `await run.done` hangs. Fix: `entered = Promise.race([entered, done.then(r => reject('run ended before the model call: '+JSON.stringify(r).slice(0,300))), timeout(10_000)])`; add `{ timeout }` to each `it`; in 8b assert `onPermit` fired.

**B5 Timing races that can fail a correct implementation or make a case vacuous.** Case 3 (`sleep(150)`, l.232) and 8a (`sleep(150)`, l.325). If B has not yet enqueued after 150 ms (full-suite load; the runner snapshots the repo first), then in case 3 `rb` is `stopped` (the first `engagedBy` read happens before the poll loop, cancel.ts:88) and a correct implementation fails; in 8a the abort lands before `acquire`, so nothing about queue withdrawal is tested and the case passes vacuously. Fix: poll `by.gemini.queue().length === 1` (with a 5 s bound) instead of sleeping; in 8a also assert the queue is empty after `queued.done`.

**B6 PHASE 2 is covered only at task level; the repo's "ACCEPTED" is the lifecycle phase.** `lifecycle/store.ts:19-31` has `ACCEPTED` as a terminal objective phase, and `lead lifecycle status` (lifecycle/cli.ts:94-98) prints `objective X: ACCEPTED` followed by bare `DONE` task lines. The operator's "a reverted implementation must never appear as currently ACCEPTED" is not tested for that surface; an implementation can satisfy every O-SA case and still print `objective M10-RL: ACCEPTED`. Fix: add a case: build a batch, `LifecycleStore.create` + transition PINNED->EXECUTING->ACCEPTING->ACCEPTED, `recordRevert` a task of its batch, run `lead lifecycle status <id>` as a subprocess, and assert (i) the historical ACCEPTED is still shown, (ii) the output marks the revert / "not currently integrated", (iii) lifecycle phase and its events are byte-identical before and after. Also make `lead status` / `renderBacklog` (`--markdown`) part of that check.

**B7 `lead tasks` assertion pins layout (would reject a correct implementation).** l.564-567 take the single line containing ` id ` and require the revert marker on THAT line. `table()` (lead.ts:48-57) already prints state reasons and "waiting on" on continuation lines; a correct implementation that prints `REVERTED ...` on the indented line below fails `assert.match(line('undone'), /revert/i)`. For `shipped`, the `doesNotMatch` is vacuous in that layout. Fix: take the block (main line plus following lines starting with 16 spaces) for each task.

### GAPS

**G1 No scheduler-level identity propagation test.** Cases 1-10 hand-build `task.runId` (l.155); case 11 stops at the workflow. Nothing proves that the id the scheduler stores (`recordRun`, via the executor's `onRunStart`) is the id the step receives, nor retry/recovery: `lead retry` sets `run_id = NULL` (store.ts:733) and starts a NEW run whose cancel must ignore the old run's orphan, and lease-expiry requeue keeps `run_id` for adoption. O-SM does not prove identity: when it passes, the process is gone anyway and the permit is released, whatever the id. Fix: one case using `src/integrations/mastra/__testing__/in-process-executor.ts` with `Scheduler`: a foreign permit of the same task id from a different run on another resource, a real run, `scheduler.stop()`, expect `stillActive == []` and the permit freed; and a variant where the foreign permit is unmarked and expect `stillActive.length == 1`.

**G2 Revert details.** (i) Compare the whole task row except `updatedAt`/`artifacts` before and after, not 3 fields. (ii) Assert `integration.history[0]` keeps `actor`, `reason`, `commit`, `at` (today `commit` could be dropped). (iii) Re-open the file store and re-read `projection` (durability is only implied through the CLI). (iv) Metrics: add a worker-path DONE (APPROVED->INTEGRATING->DONE) and check `doneByWorker`, `acceptedLocalImplementationRate`, `avgEndToEndMs`, `integrationAttempts`. (v) A dependent that is already READY/CLAIMED when its dependency is reverted: state it (blocked on next promote? must not be claimable?). `claim()` calls `dependencyStatus`, so it works if that returns non-ready; add one assertion `claim` returns nothing for it.

**G3 Unknown ownership: only the absent-marker form is tested.** Operator wants "unknown ownership fails closed" including malformed. Because the holder format is unpinned, derive malformed holders from a learned real one (after B3's fix the row copy can blank or truncate the run column / marker) or pin the capacity API. Same row-copy technique gives: marker present but empty, marker for the right run on the wrong task id.

**G4 O-PR gaps.** (i) Seed an X task `BLOCKED(dependency_failed)` whose dependency has since recovered (ESCALATED dep returned to READY) and assert a scoped promote of Y does not move it to BACKLOG (cheat h''). (ii) `promote('a', {batchId: ''})` and `{batchId: 'nope'}`: must throw or do nothing, never act globally (falsy-check bug). (iii) A Y task depending on a dead X task is BLOCKED by a Y-scoped promote (cross-batch dependency read), and a Y task depending on a DONE Z task becomes READY. (iv) State and test whether transitive dependents (a task in W depending on `z-after-y`) are evaluated. (v) `scheduler.ts:159` and `integrate.ts:120` call global `promote()`; one regression on the global path is present (O-PR 2), fine.

**G5 O-RL `lease-isolation` is implementer-authored and only checked for `ok:true` (l.795-799).** This is the v1 failure mode (a vacuous scenario passes). The plan itself says the scenario will be rewritten to use a real foreign run. Fix: also assert in the evidence what the scenario proves (cancel outcome of the target `still_active` while its own permit is held, `stopped` for an idle sibling, foreign permit created by a real run with a different runId). Do not accept `ok:true` alone.

**G6 Process: the implementer can still weaken the pre-existing contracts.** The oracle protects only its own file. `http-boundary.test.ts`, `cancellation.test.ts` (l.255-305 use unmarked holders and `engagedBy(tag)` with no run id), `worker-provider.test.ts:73` ("sees a permit on ANY resource"), `gemini-/codex-scheduler.test.ts` can be edited. Fix: pin their sha256 in `oracle.json` and fail the run when any changed. Note for the implementer: `engagedBy(tag)` WITHOUT a run id must keep returning every permit/queue entry for the tag (cancellation.test.ts:271, 295-303 and l.334, 344 of this oracle depend on it).

**G7 Runner retry loop.** `runtimeTry` re-acquires a permit for the same run (runner l.428-468). No case shows the second permit also carries the run id (a failing first call, then a blocked second call, then a cancel). Cheap to add.

**G8 Concurrent same-task runs with real provider processes.** Nothing shows that cancelling run A does not terminate run B's process group when they share a task id (O-SM runs one run). The runner's `claimExecution` file is keyed by `runId.replace(/[^A-Za-z0-9_-]/g,'_')` (workflow l.148), so `a/b` and `a_b` collide and the second run is refused as `run_restarted`; relevant to the ids added for B1.

### NITS

- N1 Error-message regexes `/already/` (l.521), `/reverted/` (l.517), `/DONE/`, `/reason/` pin wording. Assert on a thrown `StoreError` and on a stable `code`, or accept any `Error`.
- N2 l.537 `notEqual(BLOCKED)`: the real result is BACKLOG (promote's BLOCKED branch goes to BACKLOG only). Assert `['BACKLOG','READY'].includes(state)`.
- N3 l.498-501 pin that the revert is a `DONE->DONE` event in `events()` and that its reason contains "reverted". Reasonable under "append-only provenance", but it is a design decision stated only in the header; keep it, and say so in oracle.json. The `failed` status for a reverted dependency (l.530) is likewise a choice (`waiting` is defensible); the weaker, still safe, contract is `status !== 'ready'`.
- N4 `cancelRun` creates a new in-memory `SchedulerStore` per call and never closes it (l.152); the audit call then silently fails (`store.audit` -> not_found, caught). Harmless, but the audit path with a real run id is never exercised.
- N5 Classifier case (l.782) keeps the old F2 signature as `product_defect`; after the fix this signature should not occur. Keep, but say it is retained for historical evidence.
- N6 `mod()` and ROOT (l.40) assume the file sits at tests/reliability/oracle/; correct once copied, wrong in the scratchpad.

## 4. Checks that came out clean

`cancelRun` -> `cancelTaskRun`: `runId` flows through `task.runId` (cancel.ts:62), `tag` from `spec.request.contract.taskId` (l.63), `store.getTask` miss falls back to the passed row (l.61). `startRun`: `abortGraceMs: 100` and `maxAttempts: 1` give the intended orphan behaviour (runner l.485-491, 537-546); a run aborted while queued does not call the model; `permit.release()` precedes the return, so `done` implies the permit is gone for honoring doubles (case 2 relies on this: correct). Case 7 sequence (cancel waits, release after 60 ms, `stopped`) is deterministic. Case 11 inputs match coding-task-workflow-restart.test.ts. `twoObjectives` transition BACKLOG->CANCELLED is legal; `finishClaude` path READY->CODING->DONE is legal (TRANSITIONS). Guards at l.439-459 match http-boundary.test.ts:132 and 163.

Verdict: ORACLE_REJECTED as written. Apply B1-B7 (all are local edits: add the overlapping-id case, the foreign-waiter assertions, replace holder replay with a row copy, add timeouts and queue polling, add the lifecycle-status case, relax the `lead tasks` line pin), and add G1, G4(i,ii), G5 and G6 before pinning; no other redesign is needed.
