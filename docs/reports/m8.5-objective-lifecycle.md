## 2. Lifecycle

```
pin (before any claim) -> PINNED -> EXECUTING --round--> ACCEPTING -> ACCEPTED | NOT_ACCEPTED
                                       |  ^                  |
                                       v  | resume --reason  v
                       AWAITING_OPERATOR / ESCALATED     ESCALATED (oracle tampered / inconclusive / provenance broken)
                       any non-final phase -> CANCELLED
round = Scheduler.run  ->  verified review of REVIEW_PENDING  ->  integrateBatch of APPROVED
```

Integration is part of every round, not a final step: the DAG contract makes a dependent `READY` only when its dependencies are `DONE` (integrated), so its worktree contains their work. "All required tasks approved" therefore means approved *and* integrated, in dependency order, before the next layer starts.

### Verified review (Phase 1)

Reads only authoritative state: the task row, the audit event log, the review request, the git object database, and an export of the exact reviewed commit. Writes nothing to the scheduler or the worker's worktree (tested).

| Check | Fails as |
| --- | --- |
| review request names this task, head and base commit | ESCALATE |
| the audit trail shows `REVIEW_PENDING` written by the owner of the **current** claim epoch (stale or forged result) | ESCALATE |
| the run id in the review is one the task recorded | ESCALATE |
| recorded artifact directory exists, its files are hashed, `result.json` does not contradict `PASS` | ESCALATE |
| reviewed commit is still the task branch tip, and descends from the task base | ESCALATE |
| allowed-file compliance **recomputed from the commit diff** | ESCALATE |
| recorded findings under an explicit policy (block / unknown / `security_warn` -> ESCALATE; `comment_removed`, `too_large` -> REPAIR; `whitespace_reindent` acknowledged) | per policy |
| verification commands pass a toolchain-only policy | ESCALATE |
| **independent re-run of the task verifier** on the exported commit with the runtime-owned hidden tests, under the sandbox | exit != 0: REPAIR_REQUIRED; no verdict (timeout, sandbox unavailable): ESCALATE |
| worker's own verifier report | recorded, never relied on |

The independent verifier is skipped when the evidence it would verify is already untrustworthy. The full verdict (checks, evidence, hash) is written to the task's `artifacts.verifiedReviews` and the audit log **before** the decision is applied.

### Repair and escalation (Phase 2)

- `REPAIR_REQUIRED` becomes the existing `REJECTED_WITH_FEEDBACK`: a correction task within `maxReviewCorrections`; past it the store escalates the task. Previous attempts stay (`REVIEW_REJECTED` tasks, `supersededBy`, all run ids, all verdicts). The feedback is the redacted, 2000-character-bounded verifier output.
- A task on a **non-default provider** gets a correction only against `lead lifecycle authorize <objective> <task> --reason ...` (per root task, 1 to 3 uses, one spent per correction). Without it: `AWAITING_OPERATOR`, no correction task, no provider call. This sits **on top of** the scheduler's provider allow-list, which still has to name the correction task.
- Stale epoch: the fence rejects the late completion (`stale_owner`) so it never becomes a review; a review whose audit trail disagrees with the current epoch is ESCALATE.
- Dead ends (task ESCALATED / BLOCKED / RUNTIME_FAILURE / rejected with no correction), a round that changes nothing, `maxRounds` (25), an unreadable acceptance run: `ESCALATED` with every cause listed, including which tasks are already integrated (partial integration). The driver never retries a stop. Human actions (`authorize`, `resume`, `cancel`) require a reason and are audited.

### Integration (Phase 3)

`integrateBatch` unchanged: per-repository lock, reviewed commit re-checked, merge `--no-ff` into `lead-integration/<batch>` only, task oracles committed, earlier tasks' commands re-run, rollback to the pre-merge SHA on conflict or verification failure, never touches `main` or the checkout. The lifecycle adds the audit entry per task (outcome, category, integrated commit, command exit codes, conflict files) and, at acceptance, the task provenance table: task, correction-of, run ids, claim epoch, worker head, integrated commit, review verdict hashes.

### Independent acceptance (Phase 4)

| Rule | How |
| --- | --- |
| Pinned before worker execution | `pin` hashes every file and fixes commands + negative-control mode (`specHash`); refused with `oracle_pin_too_late` once any task is claimed. Acceptance also checks `pinnedAt <= first CLAIMED event` |
| Workers/reviewers cannot reach it | `pin` refuses a directory overlapping the repository, the worktrees root or the artifact root, and files escaping through symlinks. The oracle is not in any review input and is never written by the lifecycle |
| Cannot be rewritten | acceptance re-hashes first; any difference is `ESCALATED oracle_tampered` and nothing is run |
| Negative control | oracle also runs on the batch base (`refs/lead/base/<batch>`); it must fail with a real exit code. Passing, or an inconclusive result, is `NOT_ACCEPTED`. `not_applicable` needs a written reason and is recorded as skipped |
| Positive acceptance | every oracle command exits 0 on the integration tip; inconclusive (timeout, no sandbox) is `ESCALATED` |
| Clean subject | each run is a `git archive` export of a commit (no `.git`, nothing a worker left behind); a worker-created file at an oracle path is `oracle_path_occupied`, never silently overwritten |
| Evidence | per command: argv, exit code, duration, output sha256 and redacted tail; per run: commit, tree id, evidence hash; plus oracle hashes, integration tip/base, task provenance, a record-level `evidenceHash` |
| Final verdict | `ACCEPTED` is reachable only from `ACCEPTING` and only from the oracle record; a cancel that lands while the oracle runs makes the result audit evidence only |

## 3. Safety invariants (each has a test)

1. Nothing is approved on the worker's report alone (a worker that reports PASS with a passing verifier on wrong code is `REPAIR_REQUIRED`).
2. A verdict is applied only if, inside the same transaction, the lifecycle is still `EXECUTING` and the task still has the reviewed head and claim epoch. (Mutation-checked: removing the phase re-read fails the phase-only-fence test.)
3. A result from a stale claim epoch cannot complete a task, and a review that does not match the current epoch is not approved.
4. Repair is bounded by the existing correction and claim budgets; a paid-provider repair spends one operator authorization or does not exist.
5. A dependent never runs before its dependencies are integrated; a dependent of a dead end never runs.
6. A merge conflict never corrupts the integration branch (restored to the pre-merge SHA) and never reaches `main`.
7. `ACCEPTED` requires oracle integrity, pin-before-claim, provenance of every integrated commit, a passing tip and (when applicable) a failing base.
8. Cancellation writes the lifecycle phase first; late review verdicts and oracle results cannot become decisions.
9. Stops are never left by the driver itself. One driver per objective (lock with renewal).
10. No existing table, column, task state, transition or command output changed.

## 7. Known limitations

- **Mocked end to end.** The worker is a fake `Executor`; the real Mastra HTTP boundary, Ollama and Codex are not in this loop. The Mastra boundary was proved separately in M8.2, and the lifecycle only consumes the same `Executor` interface.
- **No real objective has passed an independent oracle.** The M8.1 `fmtkit-describe` oracle/`accept.sh` were deliberately not run or modified; its oracle can be pinned with `lifecycle pin` for a future approved run.
- **`lead run --batch` still works without the lifecycle.** `pin` enforces pin-before-claim only for batches that go through it, and acceptance records `pinnedBeforeFirstClaim`; nothing forbids running an un-pinned batch by hand.
- **Partial integration on failure.** Because integration is incremental, a failed objective leaves its integrated tasks on `lead-integration/<batch>` (never `main`). They are listed in the stop reason.
- **Claude-kept (`executor: claude`) tasks are not automated**: they never progress, the round changes nothing, and the lifecycle stops `ESCALATED (stalled)`.
- **Command policy is narrow on purpose** (`go test|vet|build`, `gofmt`, `npx --no-install`, `node <file>`); integration commands keep their existing stricter list (`go`, `gofmt`, validated `npx`), unchanged.
- **The review feedback contains verifier output derived from worker-written code.** It is redacted, control-stripped and capped at 2000 characters, as untrusted text, but it does reach the next worker's prompt (this is how existing rejections already work).
- **Un-blocking dependents still propagates one level per promote pass** (existing limitation); the round loop absorbs it.
- **The driver lock** is an expiring row (5 min, renewed each minute); a SIGKILLed driver blocks a new one for up to the TTL.
- **Timing flake risk** in `codex-http-smoke.test.ts` under heavy parallel load (see section 5); not caused by, and not changed by, this work.
- **Heavy tests.** The lifecycle tests run real `go vet/test` (a few seconds each warm, shared cache under `$TMPDIR`); they add about 90 s to the suite.
