# M8.2 Gemini: final safety and budget preflight before the real smoke

**Recommendation: GO for exactly one real Gemini HTTP smoke on the disposable fixture, conditional on operator approval and the five conditions in section 6.** **NO-GO for any real or private repository** until the task text is off the process list (section 4). No code was changed; this review is read-only apart from local evidence files under `.workdir/` (git-ignored).

Status labels: **CONFIRMED** (observed on the real Gemini CLI 0.63.0), **CONFIRMED-INDIRECT** (shown by evidence that implies it), **DOC-ONLY** (code or docs say so; not exercised), **UNKNOWN**, **NOT ENFORCED**, **FAIL**.

## 0. Method, and what was and was not called

No Google service, no Gemini model and no Codex model was contacted for inference. The deciding technique: the **real CLI, started by the real adapter, pointed at a stub API on `127.0.0.1` with a dummy key** (`GOOGLE_GEMINI_BASE_URL`, accepted by the CLI for localhost). The stub scripts the "model" (it emits tool calls the adapter must stop) and logs every request. That exercises the actual relaunch under Seatbelt, the real stdin-to-argv path, real config loading, the real policy engine and real tool dispatch, at zero cost.

Limits of the method: the stub does not prove the real API accepts the request shape or what it bills; incidental non-inference contact (e.g. a version check) by the CLI was only sampled (`lsof` every 250 ms on the CLI's process group: the only peer ever seen was the stub), not blocked; and a **test-only shim** (`.workdir/m8.2-gemini-preflight/shim.sh`) adds `security.auth.selectedType=gemini-api-key` to the private settings, because a base-URL override makes the CLI pick its `gateway` auth type, which headless mode rejects. A real run selects `gemini-api-key` from `GEMINI_API_KEY` alone (code read, not run). Everything else (argv, stdin, env, cwd) reaches the real CLI unchanged. No credential file and no unrelated private file was opened.

Evidence: `.workdir/m8.2-gemini-preflight/evidence/{attack,ablate-core,ablate-both,envcontrol,loop,retry503,retry429}/` (`summary.json`, `requests.jsonl`, `bodies/`, `child-env.json`, `argv-seen.txt`); driver `stub-run.ts`.

## 1. Effective configuration

| Control | Status | Evidence |
| --- | --- | --- |
| Private `GEMINI_CLI_HOME` is used | **CONFIRMED** | The CLI's own message named `<run dir>/home/.gemini/settings.json` as the user settings path; the child process environment holds `GEMINI_CLI_HOME`; the model request's "project temp directory" is inside the private home; the run dir is deleted afterwards in every run that reached the adapter's `finally` (cancel, deadline, turn limit). |
| Parent-directory settings cannot reach the run | **CONFIRMED** | A `.gemini/settings.json` in the worktree's parent that would have added shell and web tools had no effect: the tool list sent to the model stayed at six file tools. Workspace settings come from the working directory only (code). |
| Project (worktree) settings cannot reach the run | **CONFIRMED (guard)** / **DOC-ONLY (policy tier)** | Trust *does* load project config: `mcp list` showed a project-defined server `Disabled` untrusted and enabled (`Disconnected`, i.e. it tried to connect) with `GEMINI_CLI_TRUST_WORKSPACE=true`. That is exactly what `--skip-trust` sets (visible on the child). So the guard that matters is `vetWorkspace` (refuses `.gemini` and `.env` at the worktree root; unit and scheduler tested). Separately, settings-derived rules sit in the user tier and the admin policy is tier 5, and workspace *policies* are disabled in this build (`disableWorkspacePolicies = true`); both are code/doc facts, not exercised, because the guard stops a project config before the CLI starts. |
| `.env` auto-loading disabled | **CONFIRMED** | The CLI walks up from the worktree and loads the first `.env`. Positive control: with `advanced.ignoreLocalEnv` removed, a parent `.env` setting `GOOGLE_GENAI_API_VERSION` changed every request path to `/v1PARENTENV/...`. With the adapter's settings the path stayed `/v1beta/...` and the marker appeared nowhere in any request. (The project's own `.env`, an ancestor of the real smoke's worktree, was not read; it is covered by the same mechanism.) |
| `web_fetch`, shell and every other non-file tool denied | **CONFIRMED** | The model-facing tool list was exactly `list_directory, read_file, grep_search, glob, replace, write_file`. When the scripted "model" called `web_fetch`, `run_shell_command` and `google_web_search` anyway, each came back `Tool "…" not found`. No request reached the stub's exfiltration endpoints; no `/tmp` file appeared. |
| ...and the admin policy is independently effective | **CONFIRMED** | Ablation 1, allowlist removed, policy kept: the tool list was still those six. Ablation 2, **neither** control: the list grew to include `web_fetch`, `google_web_search`, `enter_plan_mode`, `invoke_agent`, `update_topic`, and **`google_web_search` actually executed** (a round trip to the API; the stub answered). `web_fetch` was stopped only by the CLI's private-IP host block, which a public URL would not hit. So each control is load-bearing: the headless default alone leaves two network tools. (`run_shell_command` is already absent in headless `auto_edit`.) |
| File tools are confined to the workspace | **CONFIRMED** | `write_file` to `/tmp/...`, `read_file` of a file outside the worktree, and a write through a symlink pointing outside were all refused by the tool ("resolves outside the allowed workspace directories": the worktree **or** the project temp dir inside the private home). This is a tool-level check in addition to the OS sandbox, and it also means the model's file tools cannot read the rest of the disk; the "broad read" caveat in the first report is therefore narrower than stated (it applies to any process the model could start, and shell is denied). |
| `--skip-trust` grants nothing beyond trust | **CONFIRMED-INDIRECT** | It sets `GEMINI_CLI_TRUST_WORKSPACE=true` on the CLI and its child (observed) and nothing else observable. What trust unlocks (project settings, hooks, MCP, `.env`, skills, agents, tool auto-approval) is neutralised as above: `vetWorkspace`, `ignoreLocalEnv`, hooks and skills off in the private settings, `--allowed-mcp-server-names` of a name nothing uses, and the admin policy. `.agents/skills` and `GEMINI.md` in a worktree are not vetted; skills are off, and `GEMINI.md` is context (prompt influence), not configuration. |
| macOS Seatbelt restrictions active | **CONFIRMED (relaunch) / UNKNOWN (live confinement)** | The sandboxed child's environment carries `SANDBOX=sandbox-exec` and `SEATBELT_PROFILE=permissive-open`; the CLI's code path for `--sandbox` on macOS is the `sandbox-exec -f <profile>` relaunch (read), and the profile's behaviour was measured earlier with decoys (writes only in the worktree and its temp dirs; the gitdir, the source repo, `/tmp` and `<home>/.gemini` denied; credentials unreadable). I could **not** observe the live process being denied: every attempted escape stopped at the tool-level path check first, so the OS layer was never reached. It is a backstop behind a working front line, which is the good case, but its live effect stays UNKNOWN. |
| Turn ceiling enforced | **CONFIRMED** | Endless distinct tool calls: exactly **25** model requests, then exit 53, `runtimeError` "turn limit exceeded", task failed, no retry. (Identical repeated calls end earlier by the CLI's loop detector, with exit 0.) |

Side facts that matter for review: a normal run made **only** the main generation requests, no classifier, token-count or other auxiliary calls (2 requests for a 2-turn task, with the model pinned); with neither control, web search adds a call to a second model.

## 3. Spend, turn and retry ceilings

| Ceiling | Status | Value and evidence |
| --- | --- | --- |
| CLI invocations | **ENFORCED** | 1 (`limitInvocations` in the smoke server; a second is refused before it starts). 1 claim, 0 runtime retries, no fallback. |
| Model turns per invocation | **ENFORCED** | 25 (`model.maxSessionTurns`), measured above. |
| Wall clock | **ENFORCED** | 300 s per call (process group SIGTERM then SIGKILL). **The real CLI was terminated this way twice** (the retry runs below): "exceeded 90000ms and was terminated with SIGTERM", no process left, run dir removed. This is the first real-binary evidence for the deadline path; cancellation by signal is still only fake-CLI tested. |
| Internal API retries | **BOUNDED, NOT COUNTED BY THE RUNTIME** | The CLI retries a failing request itself: defaults read from its code are **10 attempts per logical request, 5 s initial and 30 s maximum back-off**. Measured against a stub that always answers 503 (and separately 429): **5 requests in 90 s**, still retrying when the deadline fired; no model fallback seen. They are bounded only by the 300 s deadline (about 10 attempts in that time). Whether failed 429/5xx requests are billed: **UNKNOWN** (normally not; not verified). |
| Distinction | | A **turn** is one successful generation that may call tools (billed, at most 25). A **retry** repeats the same turn after an error (at most ~10 per turn, in practice a handful before the deadline). The 25 limit does not count retries and the deadline does not count turns; the product of the two limits, not either alone, is the bound. |
| Tokens per request | **NOT CAPPED** | No `maxOutputTokens` is set; the CLI sends `thinkingBudget: 8192` with `includeThoughts: true`. First request: ~33 KB of JSON (system prompt ~21.8k chars, tool declarations, session context, the task and the file contents), roughly 8-9k input tokens; each further turn re-sends the history (+~3.7 KB in the test). Worst case for 25 turns, my estimate only: on the order of 250-300k input and up to ~200k output/thinking tokens. A normal run for this task should take 2-4 turns. |
| **Dollar or quota ceiling** | **NOT ENFORCED** | Nothing in the runtime or the CLI stops spend at an amount; cost and quota are reported `UNKNOWN`. The only real ceiling is one the operator sets on the key. |
| Model choice | **Operator lever** | With `--model` pinned there were no auxiliary calls and no routing. Without it the CLI default is `auto` (routing and possibly a classifier call, model not known in advance). |

## 4. Task privacy

| Item | Status | Evidence |
| --- | --- | --- |
| What is on argv | **CONFIRMED, FAIL for private data** | Inside `--sandbox` the CLI reads stdin, then relaunches itself and puts it on the child's argv. The process table showed, for the sandboxed child (`node … gemini --prompt "<full text>"`): the adapter's preamble, the objective, the allowed-files line and **the full contents of every relevant file** ("module.exports = 0"). Not on argv: the key, any env value. The parent and launcher show only the one-line stub. |
| Who can read it | **CONFIRMED** | On this Mac `ps` shows other users' full command lines (root's were listed with their arguments), and this machine has other local accounts with running processes. So any local user can read the task text for the run's duration (seconds to minutes). |
| Use stdin instead? | **Not practical without a redesign** | The relaunch is the CLI's own code and happens only with `--sandbox`; without it the prompt would stay on stdin but the run would be unsandboxed, which is not acceptable. The alternatives each weaken something or change the design: a prompt file in the worktree (a forbidden mutation, and an extra model turn), `--include-directories` for a prompt dir (makes it writable in Seatbelt), or wrapping `gemini` in our own `sandbox-exec` with the CLI's own relaunch avoided (the real fix, but a redesign and untested). Not attempted, as instructed. |
| What goes to Google | **CONFIRMED** | Request 1: system instruction, six tool declarations, session context (date, OS, **absolute workspace path including your user name**, project temp dir, a directory tree of up to 200 items) and the task with the file contents. Parent `GEMINI.md`, the parent `.env`, files outside the worktree and the dummy key were **not** present. Worktree-local `GEMINI.md` would be. |
| After a hard kill | **GAP (low)** | The CLI keeps a chat transcript in the private home during a run (`…/tmp/<project>/chats/session-*.jsonl`). The adapter removes the home in `finally`. A `kill -9` of the Mastra server or harness skips that, leaving a 0700 temp dir with the transcript. My own fake-CLI tests (which hard-kill on purpose) left six such directories in `$TMPDIR`, containing only policy and settings; I removed them. |
| Smoke impact | | The smoke's content is the synthetic `Double` fixture. Exposure on argv is acceptable for it. |
