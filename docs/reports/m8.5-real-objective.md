## 12. Known limitations

- **One tiny, fully specified objective, one run, one passing outcome.** It shows the machinery works with a real worker; it says little about success rate, harder tasks, repair, or conflicts. Nothing here is a production-readiness claim.
- **The oracle is independent but not hidden from the filesystem.** It lives outside the repository, worktrees and artifact root and is hash-pinned, but Codex's `workspace-write` sandbox restricts writes, not reads; a worker could in principle read it. The pin/hash check detects tampering, not reading.
- **Repair path not exercised for real.** Mocks show a failing task stops with no second call; a real `REPAIR_REQUIRED` → `AWAITING_OPERATOR` was not observed.
- **Model unknown, cost unknown.** The CLI default model was used and not reported.
- The harness is test infrastructure under `tests/provider-smoke/` and drives the lifecycle programmatically; it does not go through `lead lifecycle run` (which uses the machine-wide capacity database and the long-running server).
- The rehearsal with the fake CLI found two things a real run would have wasted its single claim on: the task contract gate requires the constraint "tests are immutable", and the review correctly rejects a rewrite that drops existing comments (`finding:comment_removed` → repair). Both are now reflected in the fixture and the fake.
- Timing-sensitive tests in `codex-http-smoke.test.ts` were not flaky in this session (55/55 pass in the provider-smoke group).
