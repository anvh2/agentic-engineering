# M8.7A: credential isolation

**Result: implemented and verified locally** (real `codex` binary 0.161.0 against a local stub model; no cloud call, no paid Codex invocation). No real credential was read or printed: synthetic credentials carry the secrets, and real host locations were only tested for readability with `test -r`. Nothing pushed.

## 1. Threat model

| | |
| --- | --- |
| Asset | Anything the user account can read: SSH keys, cloud and CLI tokens, the Codex login, shell history, other projects' `.env`, keychain, other programs' temp files, secrets in environment variables, plus the oracle and hidden tests |
| Adversary | The model, or text that steers it (task text, repository files). It acts through the tools Codex offers |
| Exfiltration | Everything the model sees (command output included) goes to the model provider; worker-written code also runs later in the verifier sandbox |
| Trusted | The Codex launcher process (reads its own login), the runtime, the verifier sandbox's owner |
| Before M8.7A | Codex ran model commands as the user with `workspace-write`: writes confined, **reads and environment not**. M8.6 denied a few paths (oracle) on top of "read everything" |

## 3. Isolation implementation

`src/workers/providers/codex-isolation.ts`, wired into the adapter (`codex.ts`). Four layers, each tested:

1. **Filesystem allow-list.** The profile starts from the CLI's `:minimal` read set and adds only the Go toolchain directories (`discoverToolchainReadPaths`: tool directories, Homebrew keg or `/usr/local/go`, GOROOT; never anything in or above the home directory, never `/opt/homebrew`, `/usr/local`, `/Users`...). Writes: the worktree and a per-call scratch directory; `.git` and `.codex` stay read-only. No `:root` grant, and no shared temp directories (`/private/tmp`, `/private/var/tmp` are denied explicitly).
2. **Explicit denials on top:** about 50 credential locations of the account and of `CODEX_HOME` (SSH, AWS, GCP, Azure, kube, docker, gh, npm, netrc, git credentials, Codex and Claude state, shell history, Keychains, browser cookies...), the oracle, `scheduler.db`, the harness source. In allow-list mode they are redundant by construction; they protect a deny-list-only configuration and a mistaken allow-list.
3. **Environment.** The CLI's default policy hands the model's commands **every** variable of the launcher (observed: synthetic `*_API_KEY`, `*_TOKEN`, `*_SECRET_ACCESS_KEY`, `*PASSWORD` and `SSH_AUTH_SOCK` all arrived). The run pins `inherit="core"` plus a fixed set: `HOME` and `TMPDIR` are the scratch directory, `GOCACHE`/`GOPATH` inside it, git ignores every config file, Go cannot download or phone home.
4. **Tool surface**, above.

**Fail closed**, in layers: an allow-list that is too broad or would contain a protected path is refused; unsafe or unquotable paths are refused; the adapter refuses to run without `--config`, `--disable` and `--strict-config` advertised, or when the worktree overlaps a denied path; the scratch directory is per call and removed; the Mastra server (`requireIsolationCanary`, set by the real-run command) runs the canary against the real binary **before accepting work** and refuses to start if anything leaks, a tool outside the audited set appears, the launcher cannot complete a turn, or the toolchain stops working; the real-run command also runs it as preflight.

Two findings the canary exists for: `--sandbox` silently overrides a profile (so the flag is omitted), and the default environment policy leaks every secret (so it is pinned).

## 4. Credential canary results (`tests/provider-smoke/read-isolation-canary.ts`)

One real `codex exec` per mode, driven by a stub model that runs a probe script. 16 synthetic secrets (12 at well-known credential paths, 2 unlisted files under the home directory, 2 foreign files in the shared temp directories), 17 bypass probes, 8 environment probes, 7 channel probes, 3 patch-tool probes, 10 compatibility probes, 23 real host credential locations.

| | Control (old command) | Deny-list only | **Allow-list (used)** |
| --- | --- | --- | --- |
| Synthetic secrets read | 16 / 16 | 4 / 16 (only unlisted ones) | **0 / 16** |
| Bypass: traversal, symlink, directory symlink, hard link, copy, move, tar, listing (for a listed and an unlisted secret, plus the home listing) | 13 / 17 worked | 7 / 17 (unlisted only) | **0 / 17** |
| Launcher secrets in the model's environment, `SSH_AUTH_SOCK` included | 8 / 8 | 0 / 8 | **0 / 8** |
| Keychain (CLI and Security.framework), pasteboard, process list, loopback, internet, ssh-agent | blocked | blocked | **blocked** |
| Patch tool: move or delete a protected file | move worked | blocked | **blocked** |
| Real host credential locations readable (`test -r`) | 23 / 23 | 0 / 23 | **0 / 23** |
| Tools offered | wide | 3 | **3** |

Notes: the channel probes cannot discriminate in the control run (the CLI's own sandbox already blocks them there), so they were validated unsandboxed first (keychain, ssh-agent, pasteboard and 671 processes reachable; 1 process line inside). The deny-list-only column is why the allow-list is the mode that is used: it cannot protect what nobody listed. Hard links, symlinks, `cp`, `mv` and `tar` of a protected file all fail on the source read.

**The canary is itself tested:** three deliberately weakened commands must each be caught: a profile together with `--sandbox` (profile ignored, 12+ secrets read), no environment policy (secrets visible), no tool-surface switches (extra tools offered). The verdict function is unit-tested for every exposure kind, including "a probe that did not run is a failure, not a pass".

**Trusted launcher still authenticates:** with a synthetic `auth.json` in a `CODEX_HOME` that is denied to commands and a provider that requires auth, the stub received the synthetic bearer token, while the model's own `cat` of that file was refused. The launcher also writes its session state into that directory, unaffected.

## 5. Compatibility results (allow-list, real CLI)

All true: `go version`, `go build`, `go test`, `go vet`, `gofmt`, file edit by shell, file edit by `apply_patch`, worktree write; plus the protections that must keep holding: write outside the worktree blocked, write into `.git` (hooks) blocked. Also working: `rg` (Codex's bundled ripgrep), `grep`, `find`, `sed`, `awk`, `sort`. Not available to the worker by design: `git` (its git directory is unreadable, and its Xcode shim would expose python/swift/clang), `python3`, `node`, `perl`. JS tasks therefore need extra allow paths (not provided here).

Preserved (regression-tested): oracle isolation, `.git` protection, invocation budgets, restart recovery, the whole M8.5/M8.6 suites; the harness still accepts the objective with isolation on.

## 6. Remaining exposure and limitations

1. **The verifier sandbox is still a deny-list.** Worker-written code (run by the verifier, review, integration and acceptance) can read anything under the home directory that is not in the credential list or the oracle list. In the one-attempt M8.5 flow nothing from that run is fed back to the model (no second attempt, repair never granted), so the practical path to the model is closed; it is a real gap for any flow with feedback. **Recommended M8.7B: convert that sandbox to an allow-list too.**
2. **What the allow-list leaves readable** (measured): world-readable system data (`/etc`, `/usr/{share,lib}`, `/Library/Preferences`, `/Applications`, `/private/var/db` are listable), the Go toolchain directory, the target repository's worktree (`.env` files or secrets inside the repository are the model's to read), the scratch directory.
3. **Everything the model reads goes to the provider.** Isolation limits what it can read; it does not make the worktree private.
4. **Reliance on the CLI's sandbox.** Behavior is specific to codex-cli 0.161.0 on macOS (seatbelt); keychain, ssh-agent and pasteboard are blocked by the CLI's own profile, not by ours, and mach services cannot be filtered by a profile. `--strict-config`, the tool inventory and the canary guard against drift, but the canary runs at preflight and server start, **not per call**: a CLI replaced mid-run is not re-validated.
5. A worktree under `/private/tmp` (or any denied path) fails closed with an overlap error.
6. macOS only; Linux/Windows profiles were not tested.
7. The canary creates hidden synthetic files in the real home directory (removed in `finally`; none left after the runs) because the location has to be outside the shared temp directories to mean anything.
8. A real model turn with the isolated profile has not been run (no cloud). Real models may try `git`, `python3` or `node`, which fail; this can cost turns. Prompt-injection resistance is not measured, only what the commands can reach.
9. Model identity and cost remain `UNKNOWN` unless a model is pinned (`AGENTIC_CODEX_MODEL`).

## 9. Ready for one explicitly authorized real Codex objective?

**Yes, with conditions; it is not authorized by this report.** The credential exposure that existed in M8.5 and M8.6 (every readable file and every environment secret reachable by the model) is closed for the Codex worker and verified against the real binary; the real-run command validates it again at preflight and at server start and refuses otherwise. Conditions: (1) explicit approval of the run; (2) pin the model with `AGENTIC_CODEX_MODEL` for identity; (3) keep codex-cli at 0.161.0 (the canary will refuse otherwise-incompatible behavior, but a new version needs a canary pass first); (4) do not run from a worktree path under `/private/tmp`; (5) accept item 1 above (verifier sandbox deny-list) for this one-attempt objective, or do M8.7B first. Expect the real model to be somewhat more constrained than in M8.5 (no git, no interpreters).
