## 2. Phase 1: review correctness (P0)

### The defect, wider than recorded

Every decision-making git read went through `runControlledCommand`, which cuts each stream at 4,000 bytes and appends a marker. The M8 report named the HEAD-content and diff reads in `change-review.ts`. Inspection found four more places:

| Where | What was cut | Effect |
|---|---|---|
| `change-review.ts` `git show HEAD:<file>` | file at HEAD | any file above 4 KB got a false `eof_newline` block |
| `change-review.ts` `git diff` (3 forms) | the diff | security, comment-removal and whitespace checks judged a partial diff |
| `change-review.ts` `gitStatusEntries` | work-tree status | out-of-scope paths beyond 4 KB of listing were never seen |
| `verified-review.ts` `diff --name-only base head`, `diff base head` | changed-file set, diff hash | allowed-file compliance and `diffSha256` were computed on cut output; git exit codes were ignored |
| `verified-review.ts`, `integrate.ts` `diff --name-only` | rename records | with rename detection, a rename names only its destination, so a non-allowed source path deleted by a rename passed the scope check |
| `integrate.ts` `merge-base` + `diff --name-only` | failure | a failed `merge-base` gave an empty base, then an empty change list, and the scope check passed (fail-open) |
| `change-review.ts` allowed-file read | deleted file | a deleted tracked allowed file was silently skipped |

The old gate was checked against the new regression scenarios on the `bc4617d` export:
- **False `eof_newline`:** a >4 KB file that kept its newline is blocked.
- **Malicious line missed:** an added `child_process` line beyond the cut produces only that false `eof_newline`, not `security_block`.
- **Out-of-scope paths hidden:** only **68 of 120** out-of-scope paths are reported.
- **Forged rename merged:** the old integration merged a reviewed commit that renamed an out-of-scope file onto an allowed one.

### The fix

This is not a raised limit. Evidence is now read completely, and when that is impossible the gate fails closed.

- `runControlledCommand` gains an explicit `maxOutputBytes` and reports `truncated: true` when a stream exceeded it. The 4,000-byte default for model-facing tools is unchanged.
- `readGitEvidence(repo, args, {okExitCodes?, maxBytes?})` in `src/runtime/review/change-review.ts` returns the **complete** stdout or throws `EvidenceError`. It throws on output above `REVIEW_EVIDENCE_MAX_BYTES` (32 MiB), which bounds memory and is not a sample size. It also throws on a timeout, on a start failure, and on any exit code not explicitly accepted. `git diff --no-index` is the only caller that accepts exit 1.
- `inspectChange` reads every piece of evidence through `readGitEvidence`. It works per file from structured sources:
  - **Tracked allowed files:** one `ls-files -z` call.
  - **Final newline:** decided by the complete HEAD blob (`cat-file blob`).
  - **Line counts:** git `--numstat`, not text splitting.
  - **Diff scans:** whitespace classification, comment removal and the added-line security scan run on the full diff.
- **New blocking findings:**
  - `evidence_incomplete`: anything unreadable or refused, a binary change, a symlinked or non-regular allowed file, or a status listing that cannot be read.
  - `allowed_file_deleted`.

  When evidence is incomplete, `no_change` is not added, so an unreadable tree is never reported as "nothing changed".
- `WorktreeManager.inspect` turns an unreadable baseline status into an `evidence_incomplete` inspection. The task is ESCALATED for a human; it is not thrown as `RUNTIME_FAILURE`, which could be requeued into another worker run.
- `verifyReview` re-derives everything from the committed `base..head` diff, read completely with `--no-renames`:
  - **`complete_evidence`**: the changed-file set, diff hash, `diffBytes` and per-file line counts were all read in full.
  - **`committed_diff_security`**: the blocked-pattern scan over every added line.
  - **`delegation_capacity`**: the hard limit.

  If the evidence cannot be read, `allowed_files` reads "not judged", independent verification is skipped, and the verdict is ESCALATE.
- `integrateBatch` reads its scope evidence the same way: `merge-base` and `--no-renames -z` are read completely. A failure escalates as `diverged_after_review`.

The allowed-file, epoch/lease, claim, run-identity, branch-tip and lineage checks are unchanged and still run first.

## 3. Phase 2: explicit delegation capacity policy

`src/runtime/execution/delegation-capacity.ts` holds the policy. Its name avoids the existing routing `DelegationPolicy` in `delegation.ts`.

```ts
capacity?: { warnChangedLinesPerFile: number; maxChangedLinesPerTask: number }   // on TaskSpec and on a plan task
```

| Limit | Kind | Breach | Path out |
|---|---|---|---|
| `warnChangedLinesPerFile` (default 80, the M8 value) | quality, repairable | `too_large` warn → verified review `REPAIR_REQUIRED` | a correction inside the existing `maxReviewCorrections` budget. On a paid provider it also needs `lead lifecycle authorize` (`AWAITING_OPERATOR`). When the budget is exhausted the task is ESCALATED. |
| `maxChangedLinesPerTask` (default 400) | safety, hard | `capacity_exceeded` block → task ESCALATED (`review_gate_blocked`), objective ESCALATED `task_dead_end` | a human cancels it, or re-plans with an explicit larger policy (≤ `CAPACITY_CEILING` 2,000). Never retried or repaired automatically. |

- **Missing policy.** `resolveCapacity(undefined)` applies `DEFAULT_DELEGATION_CAPACITY` with `source: 'default'`. Stored specs without the field still parse. The source travels into the inspection, the review request, the task result and the verified review's evidence, so the limit that judged a change is never implicit.
- **Invalid policy.** A partial, incoherent (warn above max), over-ceiling, non-integer or unknown-key policy is a schema error, both in the scheduler `taskSpecSchema` (`createBatch`) and in the plan (`validatePlan` → `schema`). Missing fields are never filled from defaults.
- **Before claim.** `validatePlan` returns `validation.capacity`, each LOCAL_WORKER task's resolved policy. `renderPlan` prints a `capacity:` line per worker task before `--submit`. A policy on a non-worker task produces a `capacity_ignored` warning. The Lead review pack prints the policy and the measured line counts.
- **No budget expansion.** The policy only measures and routes to existing paths. It never creates a correction past `maxReviewCorrections`, never consumes a paid-repair authorization on its own, and never raises its own limit.
- `inspectChange` now **requires** `capacity`. There is no silent default inside the gate any more.

## 5. Phase 3: Agent Core contracts (design only)

The goal is a reusable core for agent-centre. Each employee may have a delegate agent that acts for them, and a CEO (coordinator) agent aligns decisions inside explicitly granted goals, policies and budgets. These are contracts only. Nothing below is implemented in M9.0.

### Invariants

1. **Principal-bound.** Every agent acts for exactly one human principal (an employee, or a role a human holds), and the binding cannot change. An agent never acts for itself.
2. **Authority is only ever a grant.** An agent has no ambient capability: no identity-attached permissions, no environment credentials. What it may do at an instant is the intersection of its unexpired, unrevoked grants.
3. **Monotone attenuation.** For every grant, `scope ⊆ parent.scope ⊆ … ⊆ authority(root grantor)`, and every limit (budget, uses, expiry) is ≤ the parent's remaining limit. This holds at issue time and is re-checked at use time, so revoking a grant revokes everything under it.
4. **No self-grant.** A grantee is never the issuer. Issuing needs the `authority.delegate` action in the issuer's own grant. A root grant's grantor is always a human principal, never an agent.
5. **Messages carry no authority.** Cross-agent communication is data. A request in a message is evaluated under the recipient's own grants, never the sender's. The CEO agent can propose, rank and ask; a decision that binds another agent's work needs a grant from a human that covers it.
6. **Everything auditable.** Every action that uses authority writes an `EvidenceRecord` naming the grant it used, before its effect is visible (the existing "evidence before decision" rule in `reviewRound`).
7. **One execution path.** Goal execution reuses the objective lifecycle, the scheduler, verified review and integration. Core adds authority checks at the existing decision points; it does not add a scheduler or a parallel state machine.
8. **Tenant-ready, not multi-tenant.** Every record carries `tenantId`, and every lookup is keyed by it. In M9 it is the constant `'local'`. Isolation (separate stores, credentials, sandboxes) is future work.
9. **The adapter owns the domain.** Git, worktrees, commits, diffs, allowed files and changed-line capacity live in the engineering adapter. Core sees opaque resource selectors, policy references by content hash, and evidence by content hash.

### Contracts

```ts
// ---- identity ------------------------------------------------------------------------------------------------------
type TenantId = string;                                     // 'local' until multi-tenancy exists
interface PrincipalRef { tenantId: TenantId; kind: 'employee' | 'role'; id: string }   // always resolvable to a human

interface AgentIdentity {
  tenantId: TenantId;
  agentId: string;                                          // unique within the tenant, never reused
  actsFor: PrincipalRef;                                    // immutable for the agent's life
  kind: 'delegate' | 'coordinator' | 'worker';              // coordinator = CEO agent; worker = an adapter's executor
  registeredBy: PrincipalRef;                               // a human; audited
  status: 'active' | 'suspended' | 'retired';               // suspended: every grant is inert until reactivated by a human
  // deliberately no permissions here: authority is only AuthorityGrant
}

// ---- authority -----------------------------------------------------------------------------------------------------
type ActionKind =
  | 'goal.propose' | 'goal.execute' | 'goal.cancel'
  | 'delegation.create'                                     // hand work to another agent under a sub-grant
  | 'authority.delegate'                                    // issue a sub-grant at all
  | 'repair.authorize'                                      // today: lead lifecycle authorize
  | `provider.use:${string}`;                               // today: allowProviders / AGENTIC_ALLOW_PROVIDERS
interface ResourceSelector { adapter: string; selector: Record<string, unknown> }   // engineering: { repository, paths? }
interface PolicyRef { kind: string; sha256: string }        // engineering: delegation-capacity, provider allow-list
interface Budget { unit: 'usd' | 'tokens' | 'invocations'; amount: number }

interface AuthorityGrant {
  tenantId: TenantId;
  grantId: string;
  grantor: PrincipalRef | { agentId: string };              // an agent only under a parent grant with 'authority.delegate'
  grantee: { agentId: string };                             // never the grantor
  parentGrantId: string | null;                             // null only when the grantor is a human principal
  scope: { actions: ActionKind[]; resources: ResourceSelector[]; policies: PolicyRef[] };
  limits: { budgets: Budget[]; maxUses?: number; expiresAt: number };   // expiry required: no open-ended authority
  reason: string;                                           // mandatory, audited
  issuedAt: number;
  revokedAt: number | null; revokedBy: PrincipalRef | null; // revocation cascades to every descendant grant
}

// ---- work ----------------------------------------------------------------------------------------------------------
interface Goal {
  tenantId: TenantId;
  goalId: string;
  owner: PrincipalRef;                                      // the accountable human
  proposedBy: { agentId: string } | PrincipalRef;
  statement: string; acceptanceCriteria: string[]; constraints: string[];
  grantIds: string[];                                       // the authority it executes under (checked, never implied)
  policies: PolicyRef[];                                    // pinned at start, like the oracle
  parentGoalId: string | null;                              // decomposition by a coordinator stays inside the parent's grants
  adapter: 'engineering';                                   // realised as an EngineeringObjective -> plan -> batch
  adapterRef: string;                                       // engineering: the objective id / batch id
  phase: LifecyclePhase;                                    // the existing objective lifecycle phases; no parallel state
}

interface Delegation {
  tenantId: TenantId;
  delegationId: string;
  goalId: string;
  from: { agentId: string } | PrincipalRef;
  to: { agentId: string };
  grantId: string;                                          // must cover the work; checked at claim and at every decision
  adapterTask: { adapter: 'engineering'; taskId: string };  // engineering: scheduler task id (DelegationRequest in its spec)
  policies: PolicyRef[];                                    // engineering: the task's delegation capacity
  budget: Budget[];                                         // ≤ the grant's remaining budget
  // state is the adapter task's state (scheduler TaskState); Core stores none of its own
}

// ---- execution and evidence ----------------------------------------------------------------------------------------
interface ExecutionContext {                                // built by the runtime only, never accepted from an agent
  tenantId: TenantId;
  actor: { agentId: string; actsFor: PrincipalRef };
  goalId: string; delegationId: string | null;
  grant: { grantId: string; chain: string[]; effectiveScope: AuthorityGrant['scope']; remaining: Budget[] };
  fence: { owner: string; epoch: number } | null;           // engineering: the claim fence
  deadline: number;
  correlationId: string;                                    // ties runs, events and evidence together
}

interface EvidenceRecord {                                  // append-only
  tenantId: TenantId;
  evidenceId: string;
  at: number;
  actor: { agentId: string | null; principal: PrincipalRef };
  grantId: string | null;                                   // null only for runtime-internal facts
  goalId: string | null; delegationId: string | null;
  kind: string;                                             // 'review.verdict' | 'integration' | 'acceptance' | 'authorization.used' | 'message' ...
  subject: { adapter: string; ref: string };                // engineering: task id + commit
  claims: Record<string, unknown>;                          // what was decided, and on which policy (e.g. capacity + source)
  contentHashes: Record<string, string>;                    // sha256 of the evidence itself (diff, verdict, oracle)
  prevHash: string; hash: string;                           // per-goal hash chain: tampering and gaps are detectable
}
```

### Core vs engineering adapter

- **Core:** identity, grants and their algebra, goals, delegations as references, execution context, evidence, the authority check.
- **Engineering adapter:** `EngineeringObjective` and plans, `TaskSpec`/`DelegationRequest`, worktrees, branches, commits, `readGitEvidence`, the review gate, delegation capacity in changed lines, integration, the pinned oracle.

Core never imports the adapter. That extends the existing rule that runtime does not import integrations.

## 6. Migration risks

1. **New default hard limit (400 lines per task).** Before M9.0, a change above 80 lines only warned. Now a task over 400 lines is ESCALATED, so objectives that produce large changes must declare `capacity` explicitly, at most 2,000.
2. **New fail-closed escalations.** These cases now escalate where they used to pass: a binary change, a symlinked or deleted allowed file, an unreadable or oversized git output, a failed `merge-base` at integration, and a rename across the scope boundary.
3. **Line counts come from `--numstat`.** For a new file this is N lines; the old split gave N+1. Thresholds move by one at the edge.
4. **Larger review records.** Diffs in `reviews.request` and the Lead review pack were cut at 4 KB per file. They are now complete, up to 32 MiB. The SQLite rows grow, and so does the review pack sent to a billed Claude Lead. Display may need its own bound that labels itself as truncated, but decisions must never read it.
5. **Persisted shape.** The `capacity` field is optional in the task spec JSON, so no migration or identifier change is needed and old rows read as the default. Older code reading a new row ignores the field and applies its own 80-line, no-hard-limit behaviour. Do not run mixed versions against one scheduler database.
6. **Verdict hashes.** `ReviewEvidence` gains `diffBytes`, `changedLines` and `capacity`, so new `verdictHash` values are computed over more fields. Stored verdicts keep their recorded bodies and hashes.
7. **Phase 3 rollout.** Adding grant checks at existing decision points can stop in-flight objectives that have no grant. The rollout needs an explicit, audited bootstrap grant per existing objective; never an implicit allow-all.

## 7. Next M9 vertical slice (proposal: M9.1 authority-scoped goal)

One employee's delegate agent runs one engineering goal through the existing lifecycle, under a human-issued grant:

1. **Store.** `agents`, `authority_grants` and an `evidence` hash chain in the existing scheduler database, behind an explicit migration, with `tenantId = 'local'`.
2. **Grant checks at the existing decision points only:** submit, claim (provider), repair authorization, integration, and acceptance. The current allow-list and `authorize` become grants.
3. **CLI.** `lead agent register`, `lead grant issue|revoke` (human only, reason mandatory), and `lead objective --as <agent>`.
4. **Tests:**
   - revocation mid-run stops the run at the next decision point;
   - an agent cannot self-grant or exceed its grantor;
   - a message cannot convey authority;
   - an expired grant fails closed;
   - every decision carries an `EvidenceRecord` with its `grantId`.
5. **Out of scope:** the CEO agent, multi-tenancy, the SaaS product, and any real model call.
