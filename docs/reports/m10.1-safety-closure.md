## 1. Outcome in one paragraph

F2 is fixed the way the M10 post-decision finding proposed and the operator specified: a permit now names the **run** that owns it, and a cancel is confirmed against that run, not against the task id and not against a provider or resource. A foreign run's permit or queue entry no longer blocks an unrelated cancel; the run's own permit and any permit whose owner cannot be established still do (fail closed), so the existing false-STOPPED contract (`http-boundary.test.ts:132`) is untouched. The scheduler now keeps execution, integration and acceptance apart: a DONE task whose code was reverted stays DONE as history and is never again "currently accepted". Promotion can be scoped to one objective, which removes the M10 side effect on the eShop tasks. The verified M10 components (fault points, deterministic smoke timeouts, Reliability Lab, `lead meeting`) are carried in. All of it is held to a hash-pinned acceptance oracle that was written, reviewed by a separate reviewer and negative-controlled **before** the implementation.

## 3. F2: run-scoped permit safety

**Root cause.** A task id is unique per plan, not per machine or per execution. `ModelCapacity.engagedBy(tag)` matched every permit carrying the task id on every resource, so two runs of one id (a codex run and a gemini run, two test files sharing one capacity database, a retry next to an orphan) blocked each other's cancel confirmation. M10's attempt to fix it by scoping to the task's resource made the cancel confirmation report STOPPED while the target's permit was still held, and was reverted.

**Fix.** `permitHolder()` writes `<label>:<taskId>:pid<pid>:run=<encodeURIComponent(runId)>`; the coding runner names every permit and queue entry of a run (every attempt and retry) with the run id; the Mastra workflow step passes its own `runId`; `cancelTaskRun` asks `engagedBy(tag, { runId })`. Provider, resource and handle are never consulted. No schema change.

**Invariants (each is an oracle case; the cases that decide each one are listed, and the mutants in section 7 break them one at a time):**

1. Another run's permit or queue entry does not block this run's cancel (cases 1, 2, 3, 4, 9b, 11, 13, 14).
2. This run's own permit or queue entry always blocks it (1, 3, 6, 13).
3. An entry whose owner cannot be read (legacy holder, missing or malformed marker) blocks every run's cancel: fail closed (10, 10b, 14, guards).
4. A provider/resource mismatch, or a probe handle on another resource, can neither hide the target's permit nor adopt a foreign one (5).
5. A provider call that outlived its abort keeps the permit until it settles; the cancel stays `still_active` meanwhile (7).
6. Cancellation while queued leaves nothing behind and takes no later permit; cancellation right after the grant, before the call, releases it (8a, 8b).
7. A crashed holder's un-renewed lease stops blocking when it expires; a live one blocks (9a); a re-run is not blocked by the previous run's stale lease (9b).
8. Run ids are compared as whole values: `run-1` vs `run-10`, `r` vs `r:1`, and ids equal to parts of the holder (12).
9. The task-level probe without a run id keeps returning every entry for the task (guard 3, `worker-provider.test.ts`, `gemini-scheduler.test.ts`).

**Identity propagation, as reviewed:** scheduler (`recordRun`) → executor (`create-run?runId=`) → Mastra workflow step (`runId`) → runner option → `permitHolder` → lease/waiter row → `cancelTaskRun(task.runId)`. Proved at four levels: runner (cases 1–10, 12, 13), workflow (11), scheduler with the in-process executor (14), and over the real HTTP hop (`gemini-http-smoke.test.ts`: the permit the server's runner holds names the run id the scheduler recorded). Retry and recovery: the runner's own retry takes a second permit with the same run id (13); `lead retry` starts a new run with a new id and the abandoned run is cancelled and confirmed on its own id.

**Rollout note.** Processes started before this change write the legacy holder, so during the changeover their permits block cancels (conservative) until they exit. Restart the Studio server (`:4111`) after merging; that is an operator step, not done here.

## 4. Scheduler acceptance truth

`DONE` stays terminal and is never rewritten. A new append-only table `integration_facts` (UPDATE and DELETE refused by triggers) records `reverted` / `reinstated` facts about a DONE task, each with actor, reason, optional commit, and one `DONE → DONE` audit event, atomically. `store.projection(task)` derives `{ execution, integration, accepted }`; `accepted` is true only for a DONE task whose code is currently integrated.

A reverted implementation: does not satisfy its dependents and cannot be claimed against (`dependencyStatus`); is excluded from `doneByWorker`/`doneByClaude`/`acceptedLocalImplementationRate`/`avgEndToEndMs` while `revertedAfterDone` reports it and the `DONE` state counts stay; makes the lifecycle driver escalate (`task_reverted`) and acceptance refuse to run; shows in `lead tasks`, `lead status`, the markdown backlog and `lead lifecycle status` (an objective already recorded ACCEPTED keeps its recorded verdict and events and is shown as "not currently accepted: … reverted since"). `lead integration revert|reinstate <task> --reason … [--commit sha]` records the fact. The table is additive (`CREATE TABLE IF NOT EXISTS`); existing rows and events are never modified.

`m10-capacity-scope` (DONE in the operational database although its change was reverted by `94f5239`) is **not** corrected here: that is an operational write. See section 11.

## 5. Objective-scoped promotion

**Why M10 moved three eShop tasks.** `lead plan` called `store.promote('plan')`, the scheduler's global pass, which evaluates every BACKLOG/BLOCKED task of every objective; three `M5-ESHOP-2A` tasks had a dependency that can never reach DONE, so they went BACKLOG → BLOCKED (scheduler events 34–36). Correct by dependency rule, but not planning's business.

`promote(actor, { batchId })` evaluates that batch and every task that depends on it, directly or transitively in any batch, and nothing else. An empty or unknown batch id is an error, never "everything". `lead plan`, objective submit, `lead cancel`, review decisions, `lead recover`, integration, and a `Scheduler.run({ batchId })` use it; `promote()` with no argument is still the global pass the scheduler needs. `Scheduler.run({ batchId })` for a batch that does not exist now throws instead of idling. Not changed: `reapExpired` is still global (it requeues expired leases of other objectives); it is lease hygiene, not promotion.

## 10. Known limitations

1. **The oracle's author is also the implementer**, and its reviewer is the same model family. Independence comes from the order (written, reviewed, pinned and negative-controlled before the code), the hash pin, the protected contract tests, and 13 wrong implementations it rejects. It was amended twice after pinning (a type annotation; one case that could not pass under any implementation) and its runner twice; the oracle amendments are disclosed in `oracle.json`.
2. **Two unexplained, non-reproduced items** (A and H in section 8).
3. **Real concurrent provider processes that share a task id are not exercised** (review gap G8); the carried smoke cases run one run. Related, pre-existing: the workflow's `claimExecution` marker sanitises the run id (`a/b` and `a_b` collide and the second is refused as `run_restarted`), which fails safe.
4. **Legacy permits fail closed.** Any process started before this change holds permits without an owner; they block every run's cancel confirmation until the process exits. Restart the Studio server after merging.
5. **The Control Center UI contract is not extended** (M13 is out of scope). A reverted task still shows as DONE there; the revert appears in its event feed as a `task.audit` event.
6. **The operational database is untouched**, so `m10-capacity-scope` still reads DONE with no revert fact until the operator records it (section 11). The first open of that database by the new binary creates the additive `integration_facts` table, which is itself a write.
7. `reapExpired` is still global (it requeues expired leases of other objectives); only `promote` was scoped.
8. `lead meeting` was not run against any live model in M10.1 (no authorisation, no calls). M10's follow-up to report local Ollama usage as zero cost instead of UNKNOWN was not part of this mission and is not done.
9. `Scheduler.run({ batchId })` for an unknown batch now throws instead of idling.
10. The full suite takes about 13.5 minutes and the candidate's heavier suite raises machine load, which makes the pre-existing racy tests (B) fail more often than on the baseline's lighter run.
11. The M10 evidence tree and mission report are not copied; they stay on `mission/m10-reliability-lab` and in the archive (sha256 `14a19168f8588b4ff28d98e655fd48e5ae26fe09d759f0a946595704ba33742b`, matched before and after).
