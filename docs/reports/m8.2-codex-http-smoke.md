## 1. HTTP execution architecture (as traced, and as exercised)

```
lead task (request.provider = "codex")
  -> Scheduler.execute                       provider authorized against the OPERATOR allow-list (scheduler process)  [provider_not_authorized before any worktree]
  -> WorktreeManager.prepare                 isolated git worktree
  -> createMastraExecutor.run                src/integrations/mastra/executor.ts  (production executor)
       POST {server}/api/workflows/coding-task-workflow/create-run?runId=<uuid>     body {}
       POST {server}/api/workflows/coding-task-workflow/start?runId=<uuid>          body {inputData: {...request, repository: <worktree>}}   (returns at once)
       GET  {server}/api/workflows/coding-task-workflow/runs/<uuid>                 poll; terminal when status is not running/pending/waiting
  -> Mastra server (HTTP)  ->  coding-task-workflow
       prepare-coding-task                   contract validation + routing gate
       run-coding-worker                     provider re-authorized against AGENTIC_ALLOW_PROVIDERS of the SERVER process; probe; exclusive-create run marker
                                             (.executions/<runId>.json: the step runs at most once per run); executeDelegation -> Codex adapter
       finalize-result
  -> Codex adapter                           codex exec --sandbox workspace-write --cd <worktree> --ignore-user-config ... -  (prompt on stdin), own process group
  -> runtime verifier                        sandboxed `go test`, inside the runner (the only source of PASS)
  -> Scheduler.complete                      fenced transitions VERIFYING -> REVIEW_PENDING + review request.  Stops there; nothing is integrated.
```

| Aspect | Fact (source) |
| --- | --- |
| Run identifier | Minted by the client (`randomUUID`, `client.ts`), reported through `onRunStart`, recorded with `store.recordRun(task, fence, runId)`. A run that starts after the task lost its fence is kept as `unrecordedRunId` and cancelled by id. |
| Provider propagation | `request.provider` (default `ollama`) travels inside `inputData`; the workflow reads it with `getInitData().provider` (`coding-task-workflow.ts`, `run-coding-worker`). |
| Allow-list, two processes | Scheduler: `authorizeProvider(..., this.allowProviders)` before worktree/executor. Server: `authorizeProvider(..., allowedProvidersFromEnv())` inside the step, before the marker, the probe or any spawn. Neither a plan nor the Lead can authorize. |
| Fencing | Every task transition carries `{owner, epoch}`. A result arriving after a timeout is discarded (`if (timedOut ...) throw`); a lost lease aborts the executor and only an operator-cancelled task cancels its run; a non-default-provider lease expiry goes to `RUNTIME_FAILURE`, never back to `READY`. |
| Cancellation | `executor.cancel` -> `POST .../runs/<id>/cancel`, then the run is polled until terminal (404 counts as terminal). `cancelTaskRun` then also requires that **no model permit or queue entry is held for the task** (`ModelCapacity.engagedBy`, which spans every resource, so it sees the `codex` permit). Only both together give `stopped`. |
| Process termination | Mastra marks a run `canceled` at once and aborts the step only if the same server process is executing it; the abort signal reaches the adapter, which signals the CLI's process group (SIGTERM, then SIGKILL after `termGraceMs`) and **keeps the call pending until the group is gone**. The runner holds the permit for as long as the call is pending. So "permit released" is the cross-process evidence that the process is gone; an HTTP 200 on the cancel is not. |
| Server lifecycle (operator's) | `npm run dev` -> `mastra dev --dir src/integrations/mastra`, rebuilds `.mastra/output/index.mjs` on every source change and restarts it. |

## 6. Known limitations

1. **Nothing here proves real Codex works inside a server-spawned process.** The adapter reads the same `HOME`/`PATH`/`CODEX_HOME` as before, and the server receives the adapter's full environment allowlist, but real sign-in and the CLI's behaviour in that setting are untested.
2. **The smoke server is not `npm run dev`.** Same workflow, same HTTP routes, same client; but no Studio, observability exporter, agents or metrics route, and a LibSQL file under the smoke directory. The production `index.ts` registers the workflow with the default registry, so the **hard invocation cap and the process ledger exist only in the smoke server**. In production the bounds are the runner's: 2 coding attempts, 0 automatic runtime retries for Codex.
3. **The cap of 1 invocation is stricter than the in-process smoke (≤ 2).** If the first attempt fails verification there is no second attempt: the smoke ends non-`REVIEW_PENDING`. That is intended.
4. **`kill -9` of the harness cannot be handled.** It would orphan the server and any Codex process. Check with the `ps` command in section 11.
5. Provider-process accounting relies on pid = process-group id (the adapter starts each CLI as a group leader) and on pids not being recycled within a run's few minutes.
6. Mastra's cancel aborts a step only if that server process is executing it; a run orphaned by a server restart is only marked `canceled` in storage. The smoke does not restart its server mid-run.
7. Inherited from the in-process results: model unknown (CLI default), cost/quota `UNKNOWN`, broad read access for commands the model runs (anything it reads goes to OpenAI), 31.7k input tokens for a five-line task unexplained, and a sandbox that confines writes but not reads.
8. `server.log` is Mastra's own stdout/stderr, not filtered. In the rehearsal it was 3 lines; Codex stderr is redacted by the adapter before it reaches any error.

## 7. Starting the Mastra server

**You do not start one for this smoke.** `npm run smoke:codex-http` starts a dedicated server on a free `127.0.0.1` port, waits for it to answer, and stops it at the end (bounded SIGTERM, then SIGKILL of that pid only). It never uses `:4111` and never touches the `mastra dev` that is running.

For reference only: serving real codex tasks from a long-lived server later would mean restarting `npm run dev` with `AGENTIC_ALLOW_PROVIDERS=codex:<taskId>` in its environment. That restarts the operator's server, so it was deliberately not done and is not needed here.
