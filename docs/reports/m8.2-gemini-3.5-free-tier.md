## 2. Does Gemini CLI 0.63.0 support the exact id?

Yes, with one new behaviour that matters. From the bundled code and then observed:

- `gemini-3.5-flash-lite` is a built-in id (`LATEST_GEMINI_FLASH_LITE_MODEL`) with its own alias entry; for an API key it reaches the API unchanged.
- **New finding.** This id is the CLI's own default "flash-lite". For that model the CLI builds a *silent fallback chain*: flash-lite, then `gemini-3.8-flash`, then `gemini-2.5-pro`. The previous pin (`gemini-2.5-flash-lite`) had a single-model chain, which is why no fallback showed in the earlier stub tests. Observed now: when the stub answered the pinned model with 404, the CLI immediately asked for **`gemini-3.8-flash`**.
- Turning the chain off in the CLI needs `experimental.dynamicModelConfiguration` plus a settings-defined chain. That is an experimental path and a bigger change than asked, so it was **not** enabled. The control is the wire guard, which already refuses any other model: the fallback attempt got a local 403, never reached the API, and the run ended non-clean.

So the CLI itself still cannot guarantee "no other model"; the loopback guard does. This is the same arrangement as the last report, now with a demonstrated fallback attempt to stop.
