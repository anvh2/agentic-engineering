# M8.4 collaboration viewer handoff to Core B

Status: **UI_ONLY_WAITING_FOR_CORE_CONTRACT**. Inspection of the Core B worktree (`feature/m9-engineering-collaboration`, `bc4617d`) found no exported collaboration/discussion/meeting read model. No production collaboration backend, tables, coordinator or event schemas were added.

The production `GET /control-center/v1/collaboration` returns `availability: NOT_AVAILABLE`, `source: unavailable`, empty arrays and an explanatory reason. The standalone development equivalent is `/api/v1/collaboration`. These are presentation responses, not Core events. They contain no fixture records. Both views remain usable while the scheduler is disconnected.

The proposed, Zod-validated **frontend presentation DTO** lives in `apps/control-center/src/collaboration-model.ts`. It is a compatibility proposal, not an agreed Core B API. Do not adopt its names as persisted event types without Core B review. The test-only example is `apps/control-center/__testing__/collaboration-fixture.ts`; production entrypoints never import it.

## Core B read interface needed

Provide an exported side-effect-free snapshot reader with stable thread, message, meeting, round, participant and invocation IDs. Reads must not coordinate meetings, start agents or consume model permits. Please include an authoritative revision/cursor for subsequent SSE integration, and distinguish missing data from empty reported collections.

| Presentation data | Required authoritative source |
| --- | --- |
| Thread title, objective/task IDs | Persisted thread metadata; task/objective links must use scheduler IDs |
| Participants and roles | Authored identities, never inferred online presence |
| Message ID, author, UTC timestamp, type, public collaboration text | Explicit agent-authored collaboration messages, excluding private reasoning, prompts, credentials and raw provider output |
| Reply relationship, evidence URLs, invocation and trace IDs | Persisted source references; unresolved or missing references must remain visible |
| Open/resolved/unknown objection state | An explicit objection lifecycle record, not an inference from silence or a later decision |
| Meeting agenda, participants, start/end times | Persisted meeting records |
| Round progress, round/invocation limits, usage/exhaustion | Coordinator-owned counters and budgets, null when unavailable |
| Agreements, unresolved disagreements, decisions | Explicit records with original source-message IDs; the viewer never derives consensus |
| Actions, owners, follow-up state | Persisted action records plus original source-message IDs |
| Meeting usage | Reported scoped input/output tokens, completeness and source; include failed/cancelled/retried call identity to prevent duplicate aggregation |

Current interface limitations: no pagination/revision/cursor exists because no authoritative Core B contract exists; invocation counts and budget exhaustion cannot be calculated safely from messages; no meeting-level token totals are inferred from unrelated scheduler calls. Production will remain NOT AVAILABLE until a Core B adapter is implemented and reviewed.

## Update and privacy behavior

The viewer polls serially every five seconds and replaces the complete snapshot. It does not append SSE deltas or accumulate token counts. Duplicate message IDs are collapsed within their owning thread and ordered by timestamp, with an ID tie-breaker. Disconnects remove displayed collaboration records until recovery. Existing scheduler SSE remains unchanged in meaning and replaces activity/usage snapshots.

Zod selects only the declared presentation fields; unknown private fields are stripped. Text is rendered as plain React text, never HTML/Markdown execution. Reference links allow HTTP(S) or same-origin absolute paths only, reject credential-bearing URLs and executable protocols. This is defense in depth: the future Gateway adapter must explicitly whitelist public collaboration text, sanitize/redact source fields, validate IDs and reject hidden reasoning before serialization. A frontend schema alone does not make arbitrary Core messages safe to expose.

Future integration: replace only the unavailable response with a Gateway-owned adapter consuming Core B's export. Map its stable IDs and explicit decisions into the presentation DTO. Add a version/revision and bounded pagination based on the agreed Core contract; then either retain replacement polling or use Core's persisted cursor for invalidation via existing SSE. Do not create a parallel event store or reconstruct collaboration from model traces.
